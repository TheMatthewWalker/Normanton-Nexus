## Phase 1: Foundation

- Three Dapper connection factories (`Services/Sql/`) — `INexusDb`/`INexusOperationsDb`/`INexusArchiveDb`, each just a captured connection string, safe as singletons.
- EF Core migrations (`Data/Migrations/`, tooling-only — see `Data/NexusMigrationContext.cs`): `EnsureCoreSchema` idempotently creates `PortalUsers`/`PortalUserDepartments`/`PortalPermissions`/`PortalUserPermissions`/`PortalSessions`/`PortalAuditLog` if missing (guarded, safe to run against a DB the Node app's knex migrations already touched); `AddPermissionGroups` adds the new `PortalPermissionGroups`/`PortalPermissionGroupPermissions`/`PortalUserPermissionGroups` tables (see the plan's "Authorization model"). Verified with `dotnet ef migrations script` — real `dotnet ef database update` against a real SQL Server is still unverified.
- Cookie authentication with a SQL-backed `ITicketStore` (`Services/Auth/PortalSessionStore.cs`) — the direct analog of `lib/sqlSessionStore.js`, reusing the same `PortalSessions` table shape (not the same row *format* — this app's `SessionData` holds a serialized `AuthenticationTicket`, not Node's JSON session blob; users re-log-in once at cutover regardless, per the plan). Cookie `SecurePolicy` is `Always` only in Production — `SameAsRequest` everywhere else, so a plain `dotnet run` + `http://localhost` smoke test actually gets the cookie back (fixed after the `Always`-everywhere default silently broke local-HTTP session persistence).
- Per-user variable idle timeout (`Services/Auth/IdleTimeoutPolicy.cs` + `IdleTimeoutValidation.cs`) — 30 min default / 5 min `ShortIdleTimeout`, matching `config.js`'s `idleTimeoutMsFor` exactly, applied every request via `CookieAuthenticationEvents.OnValidatePrincipal` (the C# equivalent of `server.js`'s per-request `cookie.maxAge` reset under `rolling:true`).
- Login flow (`Pages/Login.cshtml(.cs)` + `Services/Auth/AuthService.cs`) — faithful port of `routes/auth.js`'s `POST /login`: hardcoded-hash dummy bcrypt compare for unknown usernames, lockout at 10 failed attempts (permanent, admin-unlock only — matches `useradmin.js`, no time-based auto-unlock), IP-partitioned rate limiting (10/15 min, matching `express-rate-limit`), a fresh session key on every successful login (session-fixation defense — no explicit `regenerate()` call needed, since `PortalSessionStore.StoreAsync` always mints a new key).
- `MustChangePassword` enforcement (`Services/Auth/MustChangePasswordPageFilter.cs` + `Pages/ChangePassword.cshtml(.cs)`) — global `IAsyncPageFilter` (registered via `AddMvcOptions` so it only ever runs for Razor Page requests, never `[ApiController]`/static assets) redirecting to a real dedicated page instead of Node's `landing.js` blocking modal. Re-signs-in with the claim dropped on success so the live session updates immediately, not just the DB row.
- Role (`operator`<`admin`<`superadmin`, superadmin bypasses) + department + the new per-tile-permission authorization gates, all independent (never ANDed on one route, matching `middleware/auth.js`) — `Services/Auth/AuthorizationRequirements.cs` + `NexusPolicyProvider.cs` lets a controller write `[Authorize(Policy = "Perm:WAREHOUSE_STOCK_ADJUST")]` / `"Dept:warehouse"` / `"Role:admin"` without pre-registering every policy name at startup.
- `Services/Auth/PermissionResolver.cs` — effective permission set = direct `PortalUserPermissions` grants UNION every group's permissions via `PortalUserPermissionGroups`/`PortalPermissionGroupPermissions`, computed once at login and baked into the ticket as claims (cheap since the ticket lives server-side in SQL, not the browser cookie — no cookie-size ceiling on permission count as tile-level codes accumulate).
- `Pages/Admin/PermissionGroups*` — minimal (not the full Phase 9 UI) group create/list/manage screen, `Role:admin` gated.
- `Models/ApiResponse.cs` + `NexusExceptions.cs` + `Middleware/ApiExceptionMiddleware.cs` — the `{success,data,error}` envelope every department `[ApiController]` returns, mapped from a small exception hierarchy (C# analog of SapServer's `ApiResponse<T>`/`SapExceptionMapper`). Scoped to `/api/*` only — Razor Page requests still go through the normal HTML error page.

Originally planned for the Quality phase, built here once Engineering turned out to need it first. TLS pinning (`sap.js`'s `certs/sap-server-cert.pem`) is NOT ported — uses the system trust store; revisit once both apps are deployed against real certs.
- `Pages/Shared/_Layout.cshtml` + `wwwroot/css/site.css` — header/page-title-bar structure matches the Node app's real markup (confirmed by diffing three department HTML files — it's copy-pasted per department in Node, not templated). ## Phase 5: Finance

GL Account Groups (CRUD) + Material Costing/Actual Costs/Profit Center Data (three SAP costing proxies) + Stock Adjustments (approve/reject stock counts + Gains/Losses reporting), ported from `routes/finance.js`, the `/cost-sheet`/`/costing/*` handlers in `routes/sap.js`, the Finance-facing slice of `routes/stockcount.js`/`stockcountsql.js`, and `private/js/finance.js`.

- **Scope deliberately narrower than Node's `routes/stockcount.js`/`stockcountsql.js` (~1,750 lines combined) — researched in full, but only the ~350-line slice Finance's own Stock Adjustments tile actually calls was ported.** Research (a dedicated background investigation, not a guess) confirmed those two files are not Finance-exclusive at all: the count-creation/line-entry/bin-completion/Finished-Goods-scanning/discrepancy-resolution surface (`LOG_SUPER`-gated) is genuinely Warehouse's own feature, shared only because Node mounted both departments' needs on one router. Building all of it now would have usurped Phase 7 (Warehouse)'s own vertical slice rather than deferring cleanly to it. `StockCountController`/`StockCountHelper` cover exactly: list counts (optionally by status), a material-grouped variance report, approve, reject, and the Gains/Losses history report — all `Perm:FIN_STOCK_APPROVE`-gated (an existing legacy code, already tile-scoped in Node, no split/default-group migration needed, unlike every earlier department's coarser legacy codes). Phase 7 extends this same controller/helper with the Warehouse-side actions rather than duplicating them — see `Models/Dto/StockCountModels.cs`'s header comment for the exact route inventory deferred.
- **`GetCountReportAsync` only implements Node's `groupBy=material` variant** — `groupBy=bin` throws a clear `NexusValidationException` pointing at Phase 7, rather than silently returning wrong data. `SapQty` on each report row is *derived* (`CountedQty - VarianceQty`) rather than summed directly from the raw per-line `SapQty` column — a material can span several `(StorageType, Bin)` groups, each independently "folded" by Node's group-variance logic so only one line per group ever carries a live, non-zeroed `VarianceQty`/`VarianceValue` (summing the raw per-line `SapQty` across groups would double-count); `CountedQty` and `VarianceQty` both sum correctly across groups by construction, so deriving `SapQty` from their difference is the safe, self-consistent choice — see the method's own doc comment for the full reasoning.
- **A genuinely new permission code, not a legacy-code split**: `FIN_GL_GROUPS_MANAGE`, gating GL-group create/update/delete. Research confirmed Node's GL-group writes and all three costing proxies have *no* permission check at all beyond `requireLogin` — a real gap, not a coarse-but-present code to split. `Data/Migrations/20260902064136_SeedFinancePermissions.cs` defines the code and a default (initially empty) "Finance Administrator" group — unlike every earlier Seed*Permissions migration, there's no legacy-holder INSERT, since there were no existing holders of anything to carry forward; an admin grants the group manually. Read access to every Finance tile stays `Dept:finance`-gated only (still a tightening over Node's "any logged-in user of any department").
- **The three SAP costing proxies are consolidated under `api/finance/*`, not Node's literal `api/sap/*` mount** — `routes/sap.js` is a shared, multi-department file in Node; these three handlers (`cost-sheet`, `costing/period-balance`, `costing/profit-center`) are genuinely Finance-only in practice (only `finance.js`'s frontend ever calls them), so this port groups them with the rest of `FinanceController` rather than preserving an incidental Node file-organization artifact as if it were a stable API contract. Every other endpoint in this migration keeps Node's literal URL — this is the one deliberate exception, and it's called out here so it isn't mistaken for an oversight.
- **KST_LABELS (Material Costing's cost-breakdown component mapping) and PC_SEGMENT_MAP/PC_SEGMENT_ORDER (Profit Center Data's profit-center-code → PV/PTFE/Other business-rule table) are ported verbatim from the real Node source, re-checked directly rather than trusted from a paraphrase** — an earlier research summary's component count didn't quite match Node's actual 8-field mapping, caught before writing the port by re-reading `private/js/finance.js` directly. Both are pure frontend business logic with no server-side equivalent; must never be "derived" or approximated.
- **Material Costing's per-row Quantity/Incoterms/Country form fields are dropped, not ported** — confirmed against SapServer's real `CostSheetRequest` DTO that only `Materials[]`/`Date` are ever read server-side; the Node form collected three fields it never actually used. Porting genuinely dead UI would violate this codebase's "no speculative fields" principle.
- **Actual Costs' client-side period-net/cumulative-balance recalculation is ported verbatim, not simplified** — it deliberately ignores SAP's own year-to-date `balance`/`CumBalance` fields (`PeriodBalanceRow` carries them through unused) and instead computes `period net = debit + |credit|`, `cumulative = running sum from zero across the fetched period range`, entirely client-side. This is real, load-bearing business logic, unlike the visual simplifications below.
- **Visual/structural simplifications, matching the "clean functional approximation over pixel parity" precedent every earlier department set**: GL Account Groups' floating add/edit modal → an in-page form (multi-account entry via one-per-line textarea, not dynamic add/remove input rows); Material Costing's right-click context menu → a plain per-row "Breakdown" toggle button; the Actual Costs/Profit Center Data DataTable's per-column filter inputs are dropped; Stock Adjustments has no client-side `FIN_STOCK_APPROVE`-based tile hiding (same simplification Quality's Concessions page already made — the API's 403 is the real gate either way).

Research found the *only* export mechanism anywhere in this department is a single client-side `Blob`-based CSV builder shared by Material Costing/Actual Costs/Profit Center Data, whose filename is hardcoded `material-costing-<date>.csv` regardless of which tile produced the data (a real naming bug in the Node original) — and Stock Adjustments, despite being the most "reporting-shaped" tile (multi-section Gains/Losses report), has *zero* export in Node at all. Rather than porting a bug-for-bug client-side `Blob` CSV (or half-guessing a server-side ClosedXML replacement's exact shape under real time pressure), export was deliberately left out of this phase — flagged here as real, acknowledged scope, not an oversight, and a natural candidate for a small dedicated follow-up once a server-side export convention is decided for this app generally (Finance's Stock Adjustments Gains/Losses report and Actual Costs/Profit Center Data are the best candidates to start with).

Same DB-touching-methods-are-untestable-without-a-live-SQL-Server caveat as Sales/ProductionSchedule: GL group CRUD's success paths and every `StockCountHelper` method except `GetCountReportAsync`'s groupBy-validation and `RejectAsync`'s reason-validation open a real connection unconditionally before any other logic runs. ## Phase 6: Production

Unlike every earlier department, Production's entire SAP-facing surface already has a working, previously-proven SapServer proxy endpoint (`ProductionController.cs`/`ProductionHelpers.cs`) — no new SapServer endpoints are needed anywhere in this department.

- **Sub-phase 6a (done)**: the 7 Supervisor Reports, Batch History, and Traceability — entirely read-only (except the trace-link create), needing no `writeEvent`/`notify()` infrastructure and no SapServer calls at all. Deliberately chosen first, matching the "smallest/simplest first" precedent every earlier phase set.

### Sub-phase 6b, fourth slice: Scrap approve/reject/retry/queue

`GET /scrap/{summary,failed,entries,pending}` + `PATCH /scrap/:id/retry` + `POST /scrap/{approve,reject}` + `GET /scrap/:id/documents` + `GET /scrap-reasons`, backend + frontend, port of the scrap-management section of `routes/productionnexus.js`. Distinct from Scrap Reversal (a later 6b slice, built on `prod.ScrapMaterialDocuments.IsReversed` — `scrapDocSql()` in Node was read for context but is that slice's concern, not this one's) and from per-process entry-time scrap *recording* (`MetreProcessHelper.RecordEntryScrapAsync`, already shipped in the third slice) — this cluster is purely supervisor review/posting of already-recorded `prod.ScrapEntries` rows.

- **`POST /api/production/scrap/post` on SapServer takes the *finished-good* material/quantity/header, not a BOM component** — confirmed by reading `SapServer/Controllers/ProductionController.cs` directly (`PostScrap`, `[Route("scrap/post")]`): SapServer itself explodes the material's BOM server-side, posts one MB11/BDC per component (and an LT01 transfer order for components in storage locations 1710/1711), and returns a `BdcWrapper` (`{ Responses: BdcResponse[] }`) with one entry per component — exactly matching Node's `parseBomScrapResponse`'s `sapRaw.data.responses` unwrap. New DTOs `ScrapPostRequest`/`BdcWrapper` added to `ProductionSapModels.cs` mirroring SapServer's `BomScrapRequest`/`BdcWrapper` (`Models/Bapi/ProductionModels.cs`) field-for-field.
- **Every SAP posting response is validated the same way** (`ParseBomScrapResponse`, private to `ScrapHelper`): every entry in the `BdcWrapper` must be `Type=="S" && MessageClass=="M7" && MessageNumber=="060"`, or the whole call is treated as failed — mirrors Node's `parseBomScrapResponse` exactly, including validating *every* response in the array, not just the first.
- **Node's real `retry` route has a latent ReferenceError bug that this port deliberately does not reproduce**: `batchRef` is declared inside Node's `try` block but referenced from its `catch` block's audit call — if the process/material lookup itself throws before `batchRef` is assigned, Node would throw a *second*, unrelated error from inside the error handler. `ScrapHelper.RetryAsync` avoids this by structuring the method in two phases instead: a validation phase (not-found/unknown-process/process-record-missing — throws `NexusNotFoundException`/`NexusValidationException` directly, propagating straight out, matching Node's early `return` before ever reaching its catch) that fully resolves `material`/`batchRef` first, followed by a SAP-call-and-persist phase wrapped in its own try/catch that can safely reference `batchRef` because it's now guaranteed assigned. Same non-reproduction precedent as `SapPad`'s and `RfcRowHelpers.GetDecimal`'s bugs in SapServer's own CLAUDE.md — a real bug gets fixed by construction, not carried forward, when it's cheap to avoid and doesn't change any *intentional* behavior.
- **`ScrapHelper.ApproveAsync`/`RejectAsync` are real bulk operations, not a loop that aborts on the first failure**: each `scrapId` gets its own connection and its own try/catch (`ApproveOneAsync`/`RejectOneAsync`), run concurrently via `Task.WhenAll` — direct port of Node's `Promise.all` over the `scrapIDs` array, same "partial success is real" precedent as Mixing entry's per-tub loop.
- **The 404-vs-other-failure distinction in Approve is preserved exactly**: a `SapProxyException` with `StatusCode == 404` (SapServer genuinely has no `/scrap/post` route deployed yet) leaves the entry pending — no `IsApproved`/`SAPPosted` update at all, so it can be retried once SapServer catches up — while every other failure marks the entry `IsApproved=1, SAPPosted=0, SAPErrorMessage=...` so it shows up in the Failed queue. Getting this backwards would either lose entries into a permanently-approved-but-never-postable state (on a routine 404 during a rolling deploy) or leave genuinely-failed entries silently stuck as pending forever.
- **`GetPendingAsync` ports Node's `sys.columns` existence guard for `IsApproved`/`IsVoided` verbatim**, not simplified away — both columns were added to `prod.ScrapEntries` via an out-of-band migration this app doesn't manage (see the root CLAUDE.md-equivalent "Schema stays as-is" principle), so an environment where either hasn't been applied yet would otherwise 500 instead of just rendering an unfiltered queue.
- **`GET /scrap-reasons` (used by the retry-queue's reason dropdown) is ported here too**, even though it isn't strictly part of this cluster's own Node route block — it's small, and both this cluster's Posted Scrap retry UI and the future Drumming/metre-wizard scrap-entry UI need it; no reason to defer a 15-line read-only helper to whichever slice happens to need it first.
- **Frontend**: `Pages/Production/{ApproveScrap,PostedScrap}.cshtml(.cs)` + `wwwroot/js/production/{approve-scrap,posted-scrap}.js`, both `Dept:production` + `Perm:PROD_SUPERVISOR` gated (stacked, same convention as Open Runs/the 7 reports). Node's drill-down (`openScrapDrilldown`, a modal showing per-material scrap-entry detail for a clicked summary row) is ported as an inline expand/collapse under the clicked row instead of a real modal — no shared modal component exists yet anywhere in this port, and building one just for this one drill-down would be scope creep; same "visual-polish simplification" precedent as `reports-common.js` skipping charts.
- 1 new Helper test (`GetDocumentsAsync`'s non-positive-scrapId guard — the only path in this cluster that validates before opening a connection) + 3 new Controller tests (`ScrapApprove`/`ScrapReject`'s empty-`scrapIds`-array guard, `ScrapDocuments`'s non-positive-id guard — all Controller-level validation, same precedent as `QualityController`'s "No rows provided."/`EngineeringController`'s "material is required." checks). Real HTTP smoke test confirms both new pages (302 unauthenticated) and all 8 new/extended API routes (401 unauthenticated, including the bulk POST endpoints) behave correctly.

### Sub-phase 6b, fifth slice: SAP Reversals

`GET /reversal/{search,by-batch/:pc/:id,find}` + `PATCH /reversal/:id` + `POST /reversal/{execute,bulk}`, backend + frontend, port of the Reversal section of `routes/productionnexus.js`. One shared `Mf41Request` record added to `ProductionSapModels.cs` rather than two near-identical DTOs.
- **`POST /reversal/execute` and `PATCH /reversal/:sapPostingId` are ported backend-only, with no frontend page calling them** — confirmed by grepping every frontend file that calls `api/productionnexus` (`production-nexus.js`, `quality.js`, `landing.js`): neither route is referenced anywhere. Node's own UI only ever drives the bulk path (`/reversal/bulk`) for the actual reversal action; `execute`/the manual `PATCH` mark-as-reversed exist as real, working API surface with no in-app consumer today. Ported for API parity (a genuinely real, working Node route, not overlooked scope) since porting them is cheap, but no Razor Page was built to drive them specifically — same reasoning as the generic `RfcController`/`FunctionController` endpoints having no dedicated UI either.
- **A new exception type, `NexusUnprocessableEntityException` (422)**, was needed for `execute`'s "this document needs to be reversed using MBST" case (SAP error `M7`/`066`) — Node's `res.status(422)` for this exact case had no existing equivalent in `NexusExceptions.cs` (which previously topped out at 409/502). Added alongside the existing NotFound/Validation/Permission/Conflict/BadGateway set.
- **`ScrapHelper.ReverseJobScrapAsync` is new shared infrastructure, called from this cluster, not from anywhere within `ScrapHelper` itself** — mirrors Node's module-level `reverseJobScrap(pool, processCode, recordID, uid)` exactly: voids any not-yet-SAP-posted scrap for the job being reversed (so it can never be approved later) and reverses any already-posted scrap documents via SapServer's MBST endpoint, logging (not throwing) if any individual document's SAP reversal fails — the parent backflush reversal that triggered this cleanup must still succeed regardless of whether every scrap document could be cleanly reversed too. Both `MarkReversedAsync` (the single PATCH path) and `BulkReverseAsync`'s per-document `MarkReversedByDocumentAsync` call into it.
- **DEVIATION, deliberate — `BulkReverseAsync` does not stream progress over Server-Sent Events the way Node's `/reversal/bulk` does.** Node opens one SSE connection per bulk request (with a 20s heartbeat to survive proxy idle timeouts) so the UI can show live per-document progress while SapServer processes potentially dozens of ~15s reversals in parallel. This port runs the identical concurrent per-document SAP calls (`Task.WhenAll`, same "partial success is real" precedent as Scrap approve/reject's `ApproveOneAsync`/`RejectOneAsync`) but returns one plain JSON response instead — no SSE infrastructure exists anywhere else in this port, and building it for this one endpoint would be new infrastructure, not a port. The functional outcome (which documents reversed, which failed, why, whether a scrap-cleanup cascade ran) is byte-for-byte identical to Node's; only the live-progress UX during a large batch is not reproduced — `sap-reversals.js`'s bulk button shows a static "Reversing N documents…" state instead of a live counter/progress bar.
- **`Type=="E"`/`MessageClass`/`MessageNumber` response branching is ported exactly, including the two named special cases**: `RM`/`210` ("already reversed" — 409 on the single `execute` path, a `synced: true` non-error result on bulk, since bulk resyncs the DB from SAP's own already-reversed state rather than failing the whole batch over it) and `M7`/`066` ("must use MBST" — 422 on `execute`, a plain per-item failure message on bulk, since MBST-required documents aren't something bulk reversal can resolve on its own). Every other `E` response falls through to a generic SAP-error message, same as Node.
- **Frontend**: `Pages/Production/SapReversals.cshtml(.cs)` + `wwwroot/js/production/sap-reversals.js`, `Dept:production` + `Perm:PROD_SUPERVISOR` gated (this whole tile is supervisor-only in Node too — reversal is not an ordinary-operator action). Five search modes (material document / batch reference / material / date range / operator) dispatch to the three different GET endpoints exactly as Node's `doSearch()` does; results render as a checkbox-selectable table feeding the single bulk-reverse action.
- 6 new Helper tests (`ReversalHelperTests` — every validation-before-DB/before-SapServer-call path: `SearchAsync`'s missing-materialDocument, `FindAsync`'s all-empty-query, `MarkReversedAsync`'s missing-reversalDocumentSAP, `ExecuteAsync`'s missing-materialDocument) + 1 new Controller test (`ReversalBulk`'s empty-array guard). Real HTTP smoke test confirms the new page (302 unauthenticated) and all 6 new API routes (401 unauthenticated) behave correctly.

### Sub-phase 6b, seventh slice: Scrap Reversal

`GET /scrap-reversal/{missed,search}` + `POST /scrap-reversal/reverse{,/bulk}`, backend + frontend, port of the Scrap Reversal section of `routes/productionnexus.js`. Reverses `prod.ScrapMaterialDocuments` via SapServer's MBST endpoint — distinct from SAP Reversals (the fifth slice, reversing `prod.SAPPostings`/backflush documents via MF41), though both share the `Mf41Request` DTO and the same SSE-not-reproduced deviation.

- **CONTRACT NOTE, confirmed by reading `SapServer/Controllers/ProductionController.cs`'s `ReverseScrap` action directly**: `POST /api/production/scrap/reverse` always returns HTTP 200 with a single `BdcResponse` — never an array/wrapper, and never a non-2xx failure for a genuine ABAP-level rejection (only for a real transport/permission failure) — the same "always 200, caller reads Type" convention documented elsewhere in SapServer's own CLAUDE.md. Node's `reverseScrapDocumentItem`/`isAlreadyReversed` hedges defensively against several possible response shapes (an array under `data.responses`, the M7/067 "already reversed" code arriving via either a thrown HTTP error or a 200 body) because its author evidently didn't have this confirmed when it was written. `ScrapReversalHelper`'s private `ReverseScrapDocumentItemAsync` only needs the single-`BdcResponse`-in-a-200 path plus one generic catch for real connectivity/permission failures — simpler than Node's own code, and documented as *why* rather than silently dropping logic Node has.
- **Node does not validate `Type=="S"` on the normal-success path here, unlike `scrap/post`'s `parseBomScrapResponse`** — only the M7/067 "already reversed" case is special-cased; any other response (including, in principle, a genuine ABAP rejection) is treated as a success and the document is marked reversed with whatever `DocumentNumber` came back. This port preserves that real, unvalidated behavior exactly rather than tightening it — flagged in `ReverseScrapDocumentItemAsync`'s own comment so it isn't mistaken for an oversight on a future pass.
- **The shared `scrapDocSql(where)` SQL-fragment builder is ported as a private method** (`ScrapReversalHelper.ScrapDocSql`) taking a trusted, server-built `WHERE` fragment — never user input directly, same convention Node's own comment calls out. `GetMissedAsync` and `SearchAsync` both build on it, exactly mirroring `/scrap-reversal/missed` and `/scrap-reversal/search`'s own Node implementations.
- **`ReverseScrapDocumentItemAsync` never throws — same "never-throws contract" Node's own doc comment calls out** (bulk runs many of these concurrently via `Task.WhenAll`/`Promise.all` and one item's failure must not cancel the others) — it returns a private `ScrapReversalItemOutcome` record instead; the single `POST /scrap-reversal/reverse` action then maps a failed outcome's `Status` (400/404/409/502) onto the matching `NexusApiException`, while the bulk action passes every outcome straight through as a `ScrapReversalBulkItemResult` regardless of success.
- **DEVIATION, deliberate, same as SAP Reversals' bulk path**: `BulkReverseAsync` runs the identical concurrent per-document SAP calls Node's `/scrap-reversal/reverse/bulk` does but returns one plain JSON response instead of Node's SSE progress stream (which reuses the same event shape as `/reversal/bulk`, per Node's own comment) — no SSE infrastructure exists anywhere in this port; see `ReversalHelper.cs`'s doc comment for the full rationale, not repeated here.
- **Frontend simplification, deliberate**: Node's search UI switches between 5 single-field "modes" (by material document / batch ref / material / date range / operator) the same way SAP Reversals' does; since `/scrap-reversal/search` actually combines every provided field with AND server-side regardless of "mode," `scrap-reversal.js` shows all 7 filter fields (material document, batch ref, material, process, date from/to, operator) at once instead of mode-switching tabs — every filter Node supports is still reachable, just not gated behind a mode selector. `Pages/Production/ScrapReversal.cshtml(.cs)`, `Dept:production` + `Perm:PROD_SUPERVISOR` gated.
- 1 new Helper test (`SearchAsync`'s all-empty-query guard — the only validation-before-DB path in this cluster; `ReverseScrapDocumentItemAsync`'s own `scrapDocumentId`/`materialDocument` guard runs after opening a connection, mirroring Node's own placement of that same check inside `reverseScrapDocumentItem` after acquiring the pool, so it isn't unit-testable without a real SQL Server) + 1 new Controller test (`ScrapReversalReverseBulk`'s empty-`items`-array guard). Real HTTP smoke test confirms the new page (302 unauthenticated) and all 4 new API routes (401 unauthenticated) behave correctly.

## Hosting

**IIS via ASP.NET Core Module v2, in-process hosting model** (the ASP.NET Core Web App template's default `hostingModel="inprocess"` in the generated `web.config` — the app runs directly inside the IIS worker process, not as a separate Kestrel process behind a reverse proxy). No `UseWindowsService()` — a deliberate departure from how the Node app is hosted today (a genuine Windows Service via `node-windows`/WinSW), per explicit user preference, and also means this app ends up hosted the same way as the sibling `SapServer` repo (both IIS sites), even though the two stay separate deployed apps.

IIS hosting carries real gotchas already confirmed painfully for real on SapServer this same session (see `/home/user/SapServer/CLAUDE.md`'s "Critical Platform Constraints") that this app's own `install.ps1`/app-pool config will need to account for once they're written:
- App pool default `OnDemand` start mode delays all startup code (DI, any background scheduler) until the first real request — needs `startMode=AlwaysRunning` + `preloadEnabled=true` + IIS Application Initialization (the `/health` endpoint above is what it would warm).
- `ApplicationPoolIdentity` needs explicit `icacls` grants (read+execute on site root, Modify on any writable path) and `processModel.loadUserProfile=$false`.
- App-pool recycling can kill an in-flight Quartz.NET job — a risk the old Windows-Service hosting didn't have. Needs either `idleTimeout=00:00:00` + recycling disabled, or every scheduled job made safely resumable across a restart. Not yet decided — no Quartz.NET jobs exist yet (Phase 10).
