## Phase 1: Foundation

- Three Dapper connection factories (`Services/Sql/`) — `INexusDb`/`INexusOperationsDb`/`INexusArchiveDb`, each just a captured connection string, safe as singletons.
- EF Core migrations (`Data/Migrations/`, tooling-only — see `Data/NexusMigrationContext.cs`): `EnsureCoreSchema` idempotently creates `PortalUsers`/`PortalUserDepartments`/`PortalPermissions`/`PortalUserPermissions`/`PortalSessions`/`PortalAuditLog` if missing (guarded, safe to run against a DB the Node app's knex migrations already touched); `AddPermissionGroups` adds the new `PortalPermissionGroups`/`PortalPermissionGroupPermissions`/`PortalUserPermissionGroups` tables (see the plan's "Authorization model"). Verified with `dotnet ef migrations script` — real `dotnet ef database update` against a real SQL Server is still unverified.
- Cookie authentication with a SQL-backed `ITicketStore` (`Services/Auth/PortalSessionStore.cs`) — the direct analog of `lib/sqlSessionStore.js`, reusing the same `PortalSessions` table shape (not the same row *format* — this app's `SessionData` holds a serialized `AuthenticationTicket`, not Node's JSON session blob; users re-log-in once at cutover regardless, per the plan). Cookie `SecurePolicy` is `Always` only in Production — `SameAsRequest` everywhere else, so a plain `dotnet run` + `http://localhost` smoke test actually gets the cookie back (fixed after the `Always`-everywhere default silently broke local-HTTP session persistence).
- Per-user variable idle timeout (`Services/Auth/IdleTimeoutPolicy.cs` + `IdleTimeoutValidation.cs`) — 30 min default / 5 min `ShortIdleTimeout`, matching `config.js`'s `idleTimeoutMsFor` exactly, applied every request via `CookieAuthenticationEvents.OnValidatePrincipal` (the C# equivalent of `server.js`'s per-request `cookie.maxAge` reset under `rolling:true`).
- Login flow (`Pages/Login.cshtml(.cs)` + `Services/Auth/AuthService.cs`) — faithful port of `routes/auth.js`'s `POST /login`: hardcoded-hash dummy bcrypt compare for unknown usernames, lockout at 10 failed attempts (permanent, admin-unlock only — matches `useradmin.js`, no time-based auto-unlock), IP-partitioned rate limiting (10/15 min, matching `express-rate-limit`), a fresh session key on every successful login (session-fixation defense — no explicit `regenerate()` call needed, since `PortalSessionStore.StoreAsync` always mints a new key).
- `MustChangePassword` enforcement (`Services/Auth/MustChangePasswordPageFilter.cs` + `Pages/ChangePassword.cshtml(.cs)`) — global `IAsyncPageFilter` (registered via `AddMvcOptions` so it only ever runs for Razor Page requests, never `[ApiController]`/static assets) redirecting to a real dedicated page instead of Node's `landing.js` blocking modal. Re-signs-in with the claim dropped on success so the live session updates immediately, not just the DB row.
- Role (`operator`<`admin`<`superadmin`, superadmin bypasses) + department + the new per-tile-permission authorization gates, all independent (never ANDed on one route, matching `middleware/auth.js`) — `Services/Auth/AuthorizationRequirements.cs` + `NexusPolicyProvider.cs` lets a controller write `[Authorize(Policy = "Perm:WAREHOUSE_STOCK_ADJUST")]` / `"Dept:warehouse"` / `"Role:admin"` without pre-registering every policy name at startup.
- `Services/Auth/PermissionResolver.cs` — effective permission set = direct `PortalUserPermissions` grants UNION every group's permissions via `PortalUserPermissionGroups`/`PortalPermissionGroupPermissions`, computed once at login and baked into the ticket as claims (cheap since the ticket lives server-side in SQL, not the browser cookie — no cookie-size ceiling on permission count as tile-level codes accumulate).
- `Pages/Admin/PermissionGroups*` — minimal (not the full Phase 9 UI) group create/list/manage screen, `Role:admin` gated.
- `Models/ApiResponse.cs` + `NexusExceptions.cs` + `Middleware/ApiExceptionMiddleware.cs` — the `{success,data,error}` envelope every department `[ApiController]` returns, mapped from a small exception hierarchy (C# analog of SapServer's `ApiResponse<T>`/`SapExceptionMapper`). Scoped to `/api/*` only — Razor Page requests still go through the normal HTML error page.
- `Services/SapServerClient.cs` — typed `HttpClient` wrapper matching `sap.js`'s `makeSapToken`/axios pattern (shared-secret JWT: `{userId}`, issuer `normanton-nexus`, audience `sap-server`, 60s expiry). Originally planned for the Quality phase, built here once Engineering turned out to need it first. TLS pinning (`sap.js`'s `certs/sap-server-cert.pem`) is NOT ported — uses the system trust store; revisit once both apps are deployed against real certs.
- `Pages/Shared/_Layout.cshtml` + `wwwroot/css/site.css` — header/page-title-bar structure matches the Node app's real markup (confirmed by diffing three department HTML files — it's copy-pasted per department in Node, not templated). Styling is a clean, functional approximation, **not** pixel-accurate (`logistics.css`/`nexus-common.css` never fully captured) — department SVG badge icons also simplified to text-only. Revisit for visual parity once worth polishing.
- `Pages/Index.cshtml(.cs)` — the Hub landing page (port of `private/landing.html`), listing tiles for every department the current user belongs to (superadmin sees all 8).
- `wwwroot/js/shared/session-guard.js` — line-for-line port of `private/js/session-guard.js` (global `fetch` monkey-patch: 401 or a non-JSON body redirects to `/Login?error=session_expired`, deduped via `sessionStorage`). Must stay the first, non-deferred `<script>` in `<head>` — see `_Layout.cshtml`.
- `GET /health` — unauthenticated liveness check for IIS Application Initialization warm-up + external monitoring, matching SapServer's own `HealthController`.

**Deliberately deferred, not forgotten**: `notifications.js` and `deploy-banner.js` both need real backing features (a `Notifications`/`NotificationDeliveries` schema + `/api/notifications/*`; a `ScheduledDeployments` table + `/api/deploy/next`) that were never fully schema-confirmed during research — only inferred from `SELECT` queries, not `CREATE TABLE` statements. ## Phase 5: Finance

GL Account Groups (CRUD) + Material Costing/Actual Costs/Profit Center Data (three SAP costing proxies) + Stock Adjustments (approve/reject stock counts + Gains/Losses reporting), ported from `routes/finance.js`, the `/cost-sheet`/`/costing/*` handlers in `routes/sap.js`, the Finance-facing slice of `routes/stockcount.js`/`stockcountsql.js`, and `private/js/finance.js`.

- **Scope deliberately narrower than Node's `routes/stockcount.js`/`stockcountsql.js` (~1,750 lines combined) — researched in full, but only the ~350-line slice Finance's own Stock Adjustments tile actually calls was ported.** Research (a dedicated background investigation, not a guess) confirmed those two files are not Finance-exclusive at all: the count-creation/line-entry/bin-completion/Finished-Goods-scanning/discrepancy-resolution surface (`LOG_SUPER`-gated) is genuinely Warehouse's own feature, shared only because Node mounted both departments' needs on one router. Building all of it now would have usurped Phase 7 (Warehouse)'s own vertical slice rather than deferring cleanly to it. `StockCountController`/`StockCountHelper` cover exactly: list counts (optionally by status), a material-grouped variance report, approve, reject, and the Gains/Losses history report — all `Perm:FIN_STOCK_APPROVE`-gated (an existing legacy code, already tile-scoped in Node, no split/default-group migration needed, unlike every earlier department's coarser legacy codes). Phase 7 extends this same controller/helper with the Warehouse-side actions rather than duplicating them — see `Models/Dto/StockCountModels.cs`'s header comment for the exact route inventory deferred.
- **`GetCountReportAsync` only implements Node's `groupBy=material` variant** — `groupBy=bin` throws a clear `NexusValidationException` pointing at Phase 7, rather than silently returning wrong data. `SapQty` on each report row is *derived* (`CountedQty - VarianceQty`) rather than summed directly from the raw per-line `SapQty` column — a material can span several `(StorageType, Bin)` groups, each independently "folded" by Node's group-variance logic so only one line per group ever carries a live, non-zeroed `VarianceQty`/`VarianceValue` (summing the raw per-line `SapQty` across groups would double-count); `CountedQty` and `VarianceQty` both sum correctly across groups by construction, so deriving `SapQty` from their difference is the safe, self-consistent choice — see the method's own doc comment for the full reasoning.
- **A genuinely new permission code, not a legacy-code split**: `FIN_GL_GROUPS_MANAGE`, gating GL-group create/update/delete. Research confirmed Node's GL-group writes and all three costing proxies have *no* permission check at all beyond `requireLogin` — a real gap, not a coarse-but-present code to split. `Data/Migrations/20260902064136_SeedFinancePermissions.cs` defines the code and a default (initially empty) "Finance Administrator" group — unlike every earlier Seed*Permissions migration, there's no legacy-holder INSERT, since there were no existing holders of anything to carry forward; an admin grants the group manually. Read access to every Finance tile stays `Dept:finance`-gated only (still a tightening over Node's "any logged-in user of any department").
- **The three SAP costing proxies are consolidated under `api/finance/*`, not Node's literal `api/sap/*` mount** — `routes/sap.js` is a shared, multi-department file in Node; these three handlers (`cost-sheet`, `costing/period-balance`, `costing/profit-center`) are genuinely Finance-only in practice (only `finance.js`'s frontend ever calls them), so this port groups them with the rest of `FinanceController` rather than preserving an incidental Node file-organization artifact as if it were a stable API contract. Every other endpoint in this migration keeps Node's literal URL — this is the one deliberate exception, and it's called out here so it isn't mistaken for an oversight.
- **KST_LABELS (Material Costing's cost-breakdown component mapping) and PC_SEGMENT_MAP/PC_SEGMENT_ORDER (Profit Center Data's profit-center-code → PV/PTFE/Other business-rule table) are ported verbatim from the real Node source, re-checked directly rather than trusted from a paraphrase** — an earlier research summary's component count didn't quite match Node's actual 8-field mapping, caught before writing the port by re-reading `private/js/finance.js` directly. Both are pure frontend business logic with no server-side equivalent; must never be "derived" or approximated.
- **Material Costing's per-row Quantity/Incoterms/Country form fields are dropped, not ported** — confirmed against SapServer's real `CostSheetRequest` DTO that only `Materials[]`/`Date` are ever read server-side; the Node form collected three fields it never actually used. Porting genuinely dead UI would violate this codebase's "no speculative fields" principle.
- **Actual Costs' client-side period-net/cumulative-balance recalculation is ported verbatim, not simplified** — it deliberately ignores SAP's own year-to-date `balance`/`CumBalance` fields (`PeriodBalanceRow` carries them through unused) and instead computes `period net = debit + |credit|`, `cumulative = running sum from zero across the fetched period range`, entirely client-side. This is real, load-bearing business logic, unlike the visual simplifications below.
- **Visual/structural simplifications, matching the "clean functional approximation over pixel parity" precedent every earlier department set**: GL Account Groups' floating add/edit modal → an in-page form (multi-account entry via one-per-line textarea, not dynamic add/remove input rows); Material Costing's right-click context menu → a plain per-row "Breakdown" toggle button; the Actual Costs/Profit Center Data DataTable's per-column filter inputs are dropped; Stock Adjustments has no client-side `FIN_STOCK_APPROVE`-based tile hiding (same simplification Quality's Concessions page already made — the API's 403 is the real gate either way).
- **No CSV export was ported for any tile in this phase**, despite the migration plan flagging Finance as "the first phase that's meaningfully export-heavy." Research found the *only* export mechanism anywhere in this department is a single client-side `Blob`-based CSV builder shared by Material Costing/Actual Costs/Profit Center Data, whose filename is hardcoded `material-costing-<date>.csv` regardless of which tile produced the data (a real naming bug in the Node original) — and Stock Adjustments, despite being the most "reporting-shaped" tile (multi-section Gains/Losses report), has *zero* export in Node at all. Rather than porting a bug-for-bug client-side `Blob` CSV (or half-guessing a server-side ClosedXML replacement's exact shape under real time pressure), export was deliberately left out of this phase — flagged here as real, acknowledged scope, not an oversight, and a natural candidate for a small dedicated follow-up once a server-side export convention is decided for this app generally (Finance's Stock Adjustments Gains/Losses report and Actual Costs/Profit Center Data are the best candidates to start with).
- 8 `FinanceHelperTests` + 2 `StockCountHelperTests` + 4 `FinanceControllerTests` + 2 `StockCountControllerTests` = 16 new tests. Same DB-touching-methods-are-untestable-without-a-live-SQL-Server caveat as Sales/ProductionSchedule: GL group CRUD's success paths and every `StockCountHelper` method except `GetCountReportAsync`'s groupBy-validation and `RejectAsync`'s reason-validation open a real connection unconditionally before any other logic runs. The three costing proxies (SAP-only, no SQL at all) are fully tested, including both validation-failure and success paths.

## Phase 6: Production

### Sub-phase 6b, fourth slice: Scrap approve/reject/retry/queue

`GET /scrap/{summary,failed,entries,pending}` + `PATCH /scrap/:id/retry` + `POST /scrap/{approve,reject}` + `GET /scrap/:id/documents` + `GET /scrap-reasons`, backend + frontend, port of the scrap-management section of `routes/productionnexus.js`. Distinct from Scrap Reversal (a later 6b slice, built on `prod.ScrapMaterialDocuments.IsReversed` — `scrapDocSql()` in Node was read for context but is that slice's concern, not this one's) and from per-process entry-time scrap *recording* (`MetreProcessHelper.RecordEntryScrapAsync`, already shipped in the third slice) — this cluster is purely supervisor review/posting of already-recorded `prod.ScrapEntries` rows.

- **`POST /api/production/scrap/post` on SapServer takes the *finished-good* material/quantity/header, not a BOM component** — confirmed by reading `SapServer/Controllers/ProductionController.cs` directly (`PostScrap`, `[Route("scrap/post")]`): SapServer itself explodes the material's BOM server-side, posts one MB11/BDC per component (and an LT01 transfer order for components in storage locations 1710/1711), and returns a `BdcWrapper` (`{ Responses: BdcResponse[] }`) with one entry per component — exactly matching Node's `parseBomScrapResponse`'s `sapRaw.data.responses` unwrap. New DTOs `ScrapPostRequest`/`BdcWrapper` added to `ProductionSapModels.cs` mirroring SapServer's `BomScrapRequest`/`BdcWrapper` (`Models/Bapi/ProductionModels.cs`) field-for-field.
- **Every SAP posting response is validated the same way** (`ParseBomScrapResponse`, private to `ScrapHelper`): every entry in the `BdcWrapper` must be `Type=="S" && MessageClass=="M7" && MessageNumber=="060"`, or the whole call is treated as failed — mirrors Node's `parseBomScrapResponse` exactly, including validating *every* response in the array, not just the first.
- **Node's real `retry` route has a latent ReferenceError bug that this port deliberately does not reproduce**: `batchRef` is declared inside Node's `try` block but referenced from its `catch` block's audit call — if the process/material lookup itself throws before `batchRef` is assigned, Node would throw a *second*, unrelated error from inside the error handler. `ScrapHelper.RetryAsync` avoids this by structuring the method in two phases instead: a validation phase (not-found/unknown-process/process-record-missing — throws `NexusNotFoundException`/`NexusValidationException` directly, propagating straight out, matching Node's early `return` before ever reaching its catch) that fully resolves `material`/`batchRef` first, followed by a SAP-call-and-persist phase wrapped in its own try/catch that can safely reference `batchRef` because it's now guaranteed assigned. Same non-reproduction precedent as `SapPad`'s and `RfcRowHelpers.GetDecimal`'s bugs in SapServer's own CLAUDE.md — a real bug gets fixed by construction, not carried forward, when it's cheap to avoid and doesn't change any *intentional* behavior.
- **`ScrapHelper.ApproveAsync`/`RejectAsync` are real bulk operations, not a loop that aborts on the first failure**: each `scrapId` gets its own connection and its own try/catch (`ApproveOneAsync`/`RejectOneAsync`), run concurrently via `Task.WhenAll` — direct port of Node's `Promise.all` over the `scrapIDs` array, same "partial success is real" precedent as Mixing entry's per-tub loop.
- **The 404-vs-other-failure distinction in Approve is preserved exactly**: a `SapProxyException` with `StatusCode == 404` (SapServer genuinely has no `/scrap/post` route deployed yet) leaves the entry pending — no `IsApproved`/`SAPPosted` update at all, so it can be retried once SapServer catches up — while every other failure marks the entry `IsApproved=1, SAPPosted=0, SAPErrorMessage=...` so it shows up in the Failed queue. Getting this backwards would either lose entries into a permanently-approved-but-never-postable state (on a routine 404 during a rolling deploy) or leave genuinely-failed entries silently stuck as pending forever.
- **`GetPendingAsync` ports Node's `sys.columns` existence guard for `IsApproved`/`IsVoided` verbatim**, not simplified away — both columns were added to `prod.ScrapEntries` via an out-of-band migration this app doesn't manage (see the root CLAUDE.md-equivalent "Schema stays as-is" principle), so an environment where either hasn't been applied yet would otherwise 500 instead of just rendering an unfiltered queue.
- **`GET /scrap-reasons` (used by the retry-queue's reason dropdown) is ported here too**, even though it isn't strictly part of this cluster's own Node route block — it's small, and both this cluster's Posted Scrap retry UI and the future Drumming/metre-wizard scrap-entry UI need it; no reason to defer a 15-line read-only helper to whichever slice happens to need it first.
- **Frontend**: `Pages/Production/{ApproveScrap,PostedScrap}.cshtml(.cs)` + `wwwroot/js/production/{approve-scrap,posted-scrap}.js`, both `Dept:production` + `Perm:PROD_SUPERVISOR` gated (stacked, same convention as Open Runs/the 7 reports). Node's drill-down (`openScrapDrilldown`, a modal showing per-material scrap-entry detail for a clicked summary row) is ported as an inline expand/collapse under the clicked row instead of a real modal — no shared modal component exists yet anywhere in this port, and building one just for this one drill-down would be scope creep; same "visual-polish simplification" precedent as `reports-common.js` skipping charts.
- 1 new Helper test (`GetDocumentsAsync`'s non-positive-scrapId guard — the only path in this cluster that validates before opening a connection) + 3 new Controller tests (`ScrapApprove`/`ScrapReject`'s empty-`scrapIds`-array guard, `ScrapDocuments`'s non-positive-id guard — all Controller-level validation, same precedent as `QualityController`'s "No rows provided."/`EngineeringController`'s "material is required." checks). Real HTTP smoke test confirms both new pages (302 unauthenticated) and all 8 new/extended API routes (401 unauthenticated, including the bulk POST endpoints) behave correctly.

### Sub-phase 6b, fifth slice: SAP Reversals

One shared `Mf41Request` record added to `ProductionSapModels.cs` rather than two near-identical DTOs.
- **`POST /reversal/execute` and `PATCH /reversal/:sapPostingId` are ported backend-only, with no frontend page calling them** — confirmed by grepping every frontend file that calls `api/productionnexus` (`production-nexus.js`, `quality.js`, `landing.js`): neither route is referenced anywhere. - **DEVIATION, deliberate — `BulkReverseAsync` does not stream progress over Server-Sent Events the way Node's `/reversal/bulk` does.** Node opens one SSE connection per bulk request (with a 20s heartbeat to survive proxy idle timeouts) so the UI can show live per-document progress while SapServer processes potentially dozens of ~15s reversals in parallel. This port runs the identical concurrent per-document SAP calls (`Task.WhenAll`, same "partial success is real" precedent as Scrap approve/reject's `ApproveOneAsync`/`RejectOneAsync`) but returns one plain JSON response instead — no SSE infrastructure exists anywhere else in this port, and building it for this one endpoint would be new infrastructure, not a port. The functional outcome (which documents reversed, which failed, why, whether a scrap-cleanup cascade ran) is byte-for-byte identical to Node's; only the live-progress UX during a large batch is not reproduced — `sap-reversals.js`'s bulk button shows a static "Reversing N documents…" state instead of a live counter/progress bar.
- **`Type=="E"`/`MessageClass`/`MessageNumber` response branching is ported exactly, including the two named special cases**: `RM`/`210` ("already reversed" — 409 on the single `execute` path, a `synced: true` non-error result on bulk, since bulk resyncs the DB from SAP's own already-reversed state rather than failing the whole batch over it) and `M7`/`066` ("must use MBST" — 422 on `execute`, a plain per-item failure message on bulk, since MBST-required documents aren't something bulk reversal can resolve on its own). Every other `E` response falls through to a generic SAP-error message, same as Node.
- **Frontend**: `Pages/Production/SapReversals.cshtml(.cs)` + `wwwroot/js/production/sap-reversals.js`, `Dept:production` + `Perm:PROD_SUPERVISOR` gated (this whole tile is supervisor-only in Node too — reversal is not an ordinary-operator action). Five search modes (material document / batch reference / material / date range / operator) dispatch to the three different GET endpoints exactly as Node's `doSearch()` does; results render as a checkbox-selectable table feeding the single bulk-reverse action.
- 6 new Helper tests (`ReversalHelperTests` — every validation-before-DB/before-SapServer-call path: `SearchAsync`'s missing-materialDocument, `FindAsync`'s all-empty-query, `MarkReversedAsync`'s missing-reversalDocumentSAP, `ExecuteAsync`'s missing-materialDocument) + 1 new Controller test (`ReversalBulk`'s empty-array guard). Real HTTP smoke test confirms the new page (302 unauthenticated) and all 6 new API routes (401 unauthenticated) behave correctly.

### Sub-phase 6b, seventh slice: Scrap Reversal

`GET /scrap-reversal/{missed,search}` + `POST /scrap-reversal/reverse{,/bulk}`, backend + frontend, port of the Scrap Reversal section of `routes/productionnexus.js`. Reverses `prod.ScrapMaterialDocuments` via SapServer's MBST endpoint — distinct from SAP Reversals (the fifth slice, reversing `prod.SAPPostings`/backflush documents via MF41), though both share the `Mf41Request` DTO and the same SSE-not-reproduced deviation.

- **CONTRACT NOTE, confirmed by reading `SapServer/Controllers/ProductionController.cs`'s `ReverseScrap` action directly**: `POST /api/production/scrap/reverse` always returns HTTP 200 with a single `BdcResponse` — never an array/wrapper, and never a non-2xx failure for a genuine ABAP-level rejection (only for a real transport/permission failure) — the same "always 200, caller reads Type" convention documented elsewhere in SapServer's own CLAUDE.md. Node's `reverseScrapDocumentItem`/`isAlreadyReversed` hedges defensively against several possible response shapes (an array under `data.responses`, the M7/067 "already reversed" code arriving via either a thrown HTTP error or a 200 body) because its author evidently didn't have this confirmed when it was written. `ScrapReversalHelper`'s private `ReverseScrapDocumentItemAsync` only needs the single-`BdcResponse`-in-a-200 path plus one generic catch for real connectivity/permission failures — simpler than Node's own code, and documented as *why* rather than silently dropping logic Node has.
- **Node does not validate `Type=="S"` on the normal-success path here, unlike `scrap/post`'s `parseBomScrapResponse`** — only the M7/067 "already reversed" case is special-cased; any other response (including, in principle, a genuine ABAP rejection) is treated as a success and the document is marked reversed with whatever `DocumentNumber` came back. This port preserves that real, unvalidated behavior exactly rather than tightening it — flagged in `ReverseScrapDocumentItemAsync`'s own comment so it isn't mistaken for an oversight on a future pass.
- **The shared `scrapDocSql(where)` SQL-fragment builder is ported as a private method** (`ScrapReversalHelper.ScrapDocSql`) taking a trusted, server-built `WHERE` fragment — never user input directly, same convention Node's own comment calls out. `GetMissedAsync` and `SearchAsync` both build on it, exactly mirroring `/scrap-reversal/missed` and `/scrap-reversal/search`'s own Node implementations.
- **`ReverseScrapDocumentItemAsync` never throws — same "never-throws contract" Node's own doc comment calls out** (bulk runs many of these concurrently via `Task.WhenAll`/`Promise.all` and one item's failure must not cancel the others) — it returns a private `ScrapReversalItemOutcome` record instead; the single `POST /scrap-reversal/reverse` action then maps a failed outcome's `Status` (400/404/409/502) onto the matching `NexusApiException`, while the bulk action passes every outcome straight through as a `ScrapReversalBulkItemResult` regardless of success.
- **DEVIATION, deliberate, same as SAP Reversals' bulk path**: `BulkReverseAsync` runs the identical concurrent per-document SAP calls Node's `/scrap-reversal/reverse/bulk` does but returns one plain JSON response instead of Node's SSE progress stream (which reuses the same event shape as `/reversal/bulk`, per Node's own comment) — no SSE infrastructure exists anywhere in this port; see `ReversalHelper.cs`'s doc comment for the full rationale, not repeated here.
- **Frontend simplification, deliberate**: Node's search UI switches between 5 single-field "modes" (by material document / batch ref / material / date range / operator) the same way SAP Reversals' does; since `/scrap-reversal/search` actually combines every provided field with AND server-side regardless of "mode," `scrap-reversal.js` shows all 7 filter fields (material document, batch ref, material, process, date from/to, operator) at once instead of mode-switching tabs — every filter Node supports is still reachable, just not gated behind a mode selector. `Pages/Production/ScrapReversal.cshtml(.cs)`, `Dept:production` + `Perm:PROD_SUPERVISOR` gated.
- 1 new Helper test (`SearchAsync`'s all-empty-query guard — the only validation-before-DB path in this cluster; `ReverseScrapDocumentItemAsync`'s own `scrapDocumentId`/`materialDocument` guard runs after opening a connection, mirroring Node's own placement of that same check inside `reverseScrapDocumentItem` after acquiring the pool, so it isn't unit-testable without a real SQL Server) + 1 new Controller test (`ScrapReversalReverseBulk`'s empty-`items`-array guard). Real HTTP smoke test confirms the new page (302 unauthenticated) and all 4 new API routes (401 unauthenticated) behave correctly.

### Sub-phase 6b, eighth slice: label browser preview (labels.js, HTML half only)

`GET api/labels/process/{processCode}/{recordId}` — port of the browser-preview half of `routes/labels.js`. This is a genuinely different kind of slice from everything else in 6b: `labels.js` needs new dependencies (a barcode library, a PDF library, a raw-TCP client) nothing else in this migration needs, so it was deliberately split rather than ported as one piece — see the scope note below for exactly where the line was drawn and why.

- **SCOPE SPLIT, deliberate**: `labels.js`'s two routes that matter to Production (`GET /process/:pc/:id` — browser preview, rendered HTML the browser prints via `window.print()`) and (`POST /process/:pc/:id/print` — server-side PDF generation sent directly to a network printer over raw TCP) turned out to need almost entirely disjoint tooling once actually read closely: the preview path needs a barcode image (embedded as a base64 PNG `data:` URI) but nothing else; only the print path needs PDF layout (`buildPDF`/`drawLabelPage`, ~220 lines of QuestPDF-shaped drawing code once ported) and a raw socket client (`tcpPrint`). Building only the preview path first delivers real, immediately usable functionality (view/reprint a label from the browser, which is most of what `labelPrint()`'s actual floor usage is) without pulling in QuestPDF or a `TcpClient` port for a return that wasn't there yet. `GET /printers` and `PATCH /printers/default` are deferred alongside the print path specifically because they only exist to serve it (picking a target network printer) — nothing in this port would call them yet.
- **`GET /pallet/scan/:id`, `GET /pallet/finish/:id` and their `/print` siblings were confirmed out of scope, not overlooked** — same conclusion the Phase 6 top-level scope note already reached before any of `labels.js` was read line-by-line: these are Warehouse/Logistics pallet-builder concerns living in this file only because Node organizes by "prints a physical label," not by department.
- **Barcode generation is genuinely new dependency surface for this migration, and — unlike almost everything SAP/SQL-facing in this migration — is fully testable for real in this sandbox**: `LabelBarcodeHelper` uses ZXing.Net's `BarcodeWriterPixelData` (pure managed, raw BGRA32 pixel bytes, no OS-level graphics dependency) plus SixLabors.ImageSharp (also pure managed) to encode a real PNG — deliberately not `System.Drawing.Common`, which needs `libgdiplus` on Linux and is discouraged there since .NET 6. `LabelBarcodeHelperTests` actually decodes the produced PNG (`Image.Load` + checks real width/height), not just "the call didn't throw" — a rare case in this migration where a new piece of infrastructure could be verified end-to-end without a live SQL Server or SapServer. One of those tests (an all-whitespace input) initially asserted the wrong expectation — space is itself a valid Code 39 character in both Node's regex and this port's, so `"   "` legitimately encodes rather than returning null — caught by the test itself, not silently "fixed" by weakening the assertion; the test was corrected to match the real, correct behavior once traced through.
- **`LabelDataHelper.FetchLabelDataAsync`'s raw SQL row is mapped through a private `LabelRawRow` record, not a positional `ValueTuple`** — the row is 12 columns wide, past the point where a flat C# `ValueTuple` auto-nests into `TRest` and Dapper's positional tuple-mapping support becomes unreliable; every other tuple-mapped query in this migration stays at ≤7 columns for exactly this reason, so this one uses a named-property record instead rather than risking silent column misalignment.
- **`fetchMixingTicketsData`'s real reason for existing is preserved exactly**: a Mixing entry backflushes each tub to SAP independently, but the generic single-record fetch path would show one ticket for the whole batch's combined weight and only the first tub's SAP document — silently dropping the rest. `FetchMixingTicketsDataAsync` builds one `LabelData` per tub instead (each with its own weight/SAP document/supplier tub number), including the `?tub=N` single-tub reprint filter and the "no tub rows yet → one whole-batch ticket so printing never silently produces nothing" fallback, both ported verbatim from Node's own comments.
- **`LabelHtmlHelper.RenderPage` is pure string-building (no I/O) and is fully unit-tested for real** — `LabelHtmlHelperTests` asserts on actual rendered HTML content (status badge colour, presence/absence of the SAP-document section on an incomplete record, one `.label` div per Mixing tub, the combined multi-ticket page title), not just "didn't throw" — matching the same "genuinely testable, so genuinely tested" opportunity `LabelBarcodeHelperTests` found.
- **`LabelsController` is a new, separate controller mounted at `api/labels`** (not `api/productionnexus`), matching Node's own separate router mount (`app.use('/api/labels', requireLogin, labelsRoutes)`) — and deliberately carries no `Dept:`/`Perm:` policy beyond `NexusControllerBase`'s own `[Authorize]`, since no route in `labels.js` checks department or a permission code either, only that the caller is logged in at all. Confirmed by reading every route in the file, not assumed.
- **Frontend**: no new page — the browser-preview route is linked directly from where Node's own reprint button lived: a "🖨 Print Label" link appended to `metre-entry.js`'s/`mixing-entry.js`'s post-submit result (opens the new record's label in a new tab) and to `metre-data.js`'s row-detail expand (added now that the route it was deferred pending actually exists — see the seventh slice's note about dropping that button entirely; it's real now, not stubbed).
- 5 new `LabelBarcodeHelperTests` + 4 new `LabelHtmlHelperTests` (both fully real, see above) + 2 new `LabelsControllerTests` (unsupported-process-code and non-positive-record-id guards — the only validation-before-DB paths in `LabelsController`). Real HTTP smoke test confirms the new route requires authentication for both a valid and an invalid process code, and every touched JS file still serves 200.
- **Still deferred, tracked as its own remaining piece of Sub-phase 6b**: server-side PDF generation (`buildPDF`/`drawLabelPage`/`buildLabelsPDF`) via QuestPDF, embedding a barcode image inside a PDF (same `LabelBarcodeHelper` PNG bytes, different embed API), a raw-TCP `TcpClient` port of `tcpPrint`, and `GET /printers`/`PATCH /printers/default`/`POST /process/:pc/:id/print` themselves.

### Sub-phase 6b, ninth slice: server-side label printing (labels.js PDF/raw-TCP half)

`POST api/labels/process/{pc}/{id}/print` + `GET api/labels/printers` + `PATCH api/labels/printers/default` — the half of `labels.js` deliberately deferred by the eighth slice. Completes label printing end-to-end: browser preview (already shipped) plus now a real "send this label straight to a network printer" action.

- **`LabelPdfHelper` is NOT a pixel-for-pixel port of Node's PDFKit drawing, and says so in its own doc comment** — PDFKit draws with absolute x/y cursors and hand-measured font sizes per field (checked once, by the original author, against real values); QuestPDF's layout model is declarative (Row/Column/constraint-based) and doesn't map cleanly onto that coordinate math. Rather than fight QuestPDF's engine to replicate PDFKit's exact numbers — a project impossible to visually verify in this sandbox anyway (no PDF viewer, no real printer) — the same content and grouping (header bar, two-column Batch Reference+barcode/Material+barcode left, SAP Material Document+barcode/Operators/Machine/Completed right, footer) is reproduced with QuestPDF's own idiomatic elements. `LabelPdfHelperTests` verifies what's actually checkable instead: valid `%PDF`-prefixed bytes, correct page count (one per label — one per Mixing tub, matching Node's one-job-per-batch `tcpPrint` design), and no exception across every real data shape (open/complete/no-machine/no-SAP-document/A4/A5).
- **QuestPDF's strict layout validation caught a real bug this port would otherwise have shipped**: the first version of the barcode-embedding helper fixed a target *height* and let width float (mirroring the shape, not the substance, of Node's own `bcImg`/`renderedH`, which actually fixes *width* and lets height follow the barcode's aspect ratio). A long batch reference encodes to a short, wide barcode image; forcing that to a tall fixed height blew the resulting width past the two-column layout's available space. PDFKit would have silently drawn the oversized image past its intended bounds — QuestPDF instead throws `DocumentLayoutException` before ever producing a PDF. Fixed by constraining on width (`MaxWidth` + `.FitWidth()`), which is what Node's own code actually does — this was a genuine port-fidelity bug (a superficial rather than substantive read of `bcImg`), caught only because QuestPDF's stricter validation surfaced it immediately in a real, ordinary test run rather than as a silent visual defect nobody would notice until a real print job came out wrong.
- **FURTHER SIMPLIFICATION, deliberate, documented in `LabelPdfHelper.BuildLabelsPdf`'s own doc comment**: content auto-sizes to whatever height it actually needs rather than being pinned to Node's fixed 420pt/148mm content box (which existed so an A4 label sits in the top half of the sheet, not stretched full-page). QuestPDF enforces strict content-must-fit constraints — a hand-tuned fixed height here would have reintroduced exactly the same class of `DocumentLayoutException` risk the barcode fix above just caught, the moment any real field's content ran longer than what was manually checked, with no PDF viewer in this sandbox to catch it before a real deploy. The trade-off is real (an A4 label now fills more of the page than Node's did) but was made deliberately, not discovered by accident.
- **`GET /printers`/`PATCH /printers/default` read/write `dbo.PortalUsers.DefaultPrinterID` via `INexusDb`, not `INexusOperationsDb`** — matching Node's own `getNexusPool()` call for these two routes specifically (every other `labels.js` route, including the print action itself, reads production data from NexusOperations) — confirmed by reading Node's implementation, not assumed from the rest of the file's pattern.
- **`LabelPrinterOptions`/`LabelPrinterConfig` (new `Services/LabelPrinterOptions.cs`) replace `config.json`'s top-level `printers` array** — bound from a new `LabelPrinters` section in `appsettings.json` (a wrapping object with a `Printers` list, matching this app's existing Options-binding convention, not a bare root-level array) rather than the bare array Node's `config.js` exposes as `printersConfig`. Same `Id`/`Name`/`Host`/`Port`/`PaperSize` fields as Node's config shape.
- **QuestPDF requires `QuestPDF.Settings.License = LicenseType.Community` before any `GeneratePdf()` call, or it throws** (a 2023 licensing change) — set both in `Program.cs` (documents the requirement for a reader scanning startup) and, belt-and-braces, in `LabelPdfHelper`'s own explicit static constructor, since `NormantonNexus.Tests` never runs `Program.cs` and would otherwise hit the same exception on the very first test. An explicit static constructor was needed rather than a field initializer — the "beforefieldinit" JIT optimization can defer a bare field initializer's execution past the point a static method is actually called, which is exactly what happened here on the first attempt.
- **`LabelPrintHelper.SendToPrinterAsync` (the `tcpPrint` port) waits for the printer to close its end of the connection before returning**, not just for the local write to complete — mirrors Node's `sock.on('close', () => resolve())` exactly (as opposed to resolving as soon as `sock.write()`'s callback fires), via a half-close (`Shutdown(SocketShutdown.Send)`) followed by draining reads until EOF, with the same 15s timeout Node's `sock.setTimeout(15000)` uses.
- **Frontend**: no new page — `metre-data.js`'s row-detail expand (already carrying the "🖨 Print Label" preview link from the eighth slice) gains a "🖨 Send to Printer…" control that lazily fetches the printer list on first click, lets the user pick one (pre-selecting their saved default), and POSTs the print request — completing both halves of Node's original single reprint button.
- 4 new `LabelPdfHelperTests` (real PDF generation + page-count verification, see above) + 4 new `LabelsControllerTests` (unsupported process code, no printers configured, unknown `printerId` — all validation-before-DB paths in `PrintProcess`). Real HTTP smoke test confirms all 3 new API routes require authentication and the app still starts cleanly with the new `IOptions<LabelPrinterOptions>`/QuestPDF wiring in place.
- **Label printing (`routes/labels.js`) is now fully covered for Production's purposes** — every route Node has for the 7 supported process codes is ported; only the explicitly-out-of-scope pallet-builder routes (Warehouse/Logistics concern) remain unported, by design.

- **The hard block reuses the just-downloaded, in-memory BOM rows from this same request — not a fresh `LatestBomSnapshotAsync` re-read**, unlike `MetreProcessHelper.CompleteAsync`. This is a real, deliberate difference from the wizard (which re-reads because draft and complete are two separate requests, possibly far apart in time and after a "Refresh BOM"); Drumming has no such gap to bridge, so it validates against exactly what it just fetched and persisted a few lines earlier, matching Node's own `drBomRows` variable reuse exactly.
- **The `BLOCKED` outcome is a genuine HTTP 409 with `success:false`, unlike every other Production write action's `SAP_FAILED`/HTTP-201 convention** — preserved exactly as a real, deliberate difference in Node itself (`res.status(409).json({ success: false, data: {...}, error: errMsg })`), not normalized away to match the wizard's `MarkMetreSapFailedAsync` pattern. `DrummingSubmitResult.Status` carries `"BLOCKED"`/`"SAP_FAILED"`/`"COMPLETE"`; the controller maps `BLOCKED` to `StatusCode(409, ...)` with an explicit `ApiResponse<T>` construction (`success:false` + populated `data` + `error`) since `ApiResponse<T>.Fail` alone can't carry a `data` payload alongside the error — every other status still returns 201.
- **`drumRef` is genuinely hyphenated (`DR-00000123`), unlike every other process's `{code}{recordId:D8}` format (`EX00000005`)** — preserved exactly per Node's own `` `DR-${String(drummingID).padStart(8, '0')}` ``. The re-drum-reversal error message quotes the *unhyphenated* form instead (`DR00000123`) — a real, separate Node inconsistency between the two, preserved as-is rather than "fixed" to match either convention, per this migration's established precedent (SapServer's `CLAUDE.md` documents several similar real-behavior-over-tidiness calls).
- **`MetreProcessHelper.RecordScrapAsync` made `internal` and reused as-is** — Drumming is never `"EX"`, so it always takes the proportional-share branch, the exact same math Node's own `submitDrumming` duplicates inline a third time (Node has no shared function between `entry`, `complete`, and `submitDrumming` for this). A real simplification over Node's structure, not a functional change, same judgment call the second slice already made for `EnterAsync`/`CompleteAsync`.
- **The concession-covered goods-movement path and the SAP-failure catch block are otherwise a straight, unremarkable reuse of the second slice's own patterns** (`BomHelper.BuildActualComponentList`, `SapGoodsMovementRequest`, the `catch (Exception sapErr) when (sapErr is not NexusApiException)` filter that lets a genuine SapServer-connectivity failure surface as a real 502/503 rather than being swallowed into a 201) — nothing new to say about these beyond "same as `MetreProcessHelper.CompleteAsync`."
- **Still not resolved**: the soft cross-department dependency the earlier research phase flagged — `AssertParentBatchesReversedAsync` depends on `prod.Drumming.IsReversed`, a flag only Warehouse/Staging's `redrumReversal.js` (not yet ported — Phase 7) ever sets. Until Warehouse ships, no drum in this new database can ever actually satisfy the re-drum check; this is expected and matches the real Node app's own inter-department ordering, not a gap introduced by this migration's phase sequencing.
- **Still real, tracked, unbuilt scope after this slice**: Failed Backflush's five-way per-process retry queue (now unblocked — its DR branch re-invokes almost all of this slice's own posting logic), Drumming coils/reversal-status/ticket-print (`GET drumming/:id/coils`, `GET drumming/:id/reversal-status`, `GET drumming/ticket/:referenceDocument/:item/print` + `loadDrummingTicketData`/`buildDrummingTicketHTML`), `GET drumming/data`, and Order Lookup. Frontend deliberately not built in this slice, same reasoning as the wizard's own second-slice note — Drumming's entry form is a substantial standalone UI (coil-length list entry, parent-batch/tub pickers, raw-material-batch entry, scrap entry) that doesn't fit any existing page shape yet.
- 5 new `DrummingHelperTests` (every request-shape validation path — empty/over-limit `coilLengths`, missing `material`/`packagingId`, non-positive `weightKg` — all before ever opening a connection, same caveat as everywhere else in this migration: the SAP-posting/hard-block/braid-consumption paths need a live SQL Server and SapServer to exercise for real).

### Sub-phase 6c, fourth slice: Failed Backflush's five-way retry queue

`GET failed-backflush` + `PATCH failed-backflush/:pc/:id/retry` + `PATCH failed-backflush/:pc/:id/cancel` (`FailedBackflushHelper`) — port of the supervisor-facing retry queue for every `Status=6` (SAP_FAILED) production record. This was the piece the first slice's own "still real, tracked, unbuilt scope" note explicitly called out as blocked on Drumming's entry flow landing first, since the DR retry branch re-invokes almost all of `DrummingHelper`'s own posting logic — it's unblocked now that the third slice shipped.

- **Five genuinely different retry shapes dispatched off one process code, matching Node's own single route handler exactly** (`ProductionSapHelpers.Process`/`MetreProcesses` already had every code/table/pk this needed): MX retries per individually-failed tub (`prod.MixingTubs.SAPSuccess=0`), never the whole mix at once — a failing tub's own SAP error is caught right there and recorded per-tub, so one bad tub never stops the rest from retrying. DR re-runs almost the exact hard-block/concession/backflush sequence `DrummingHelper.SubmitAsync` itself uses. EX/CO/BR/CL/TW re-post a plain ZF40N backflush (EX additionally re-gates on MX-tub staging via the wizard's own `ValidateMxTubLinksAsync`/`ApportionMxExpectedConsumptionAsync`, both made `internal` for this reuse). EW/HA have no SAP call at all — "retry" there just means a supervisor reviewed the record and marked it complete. FW/an unknown code returns "Retry not yet implemented," matching Node's own fallthrough.
- **A confirmed, genuine bug in Node's own DR non-concession retry branch was found and fixed, not faithfully reproduced.** Node's retry route calls `sapPost(\`/drumming/${entryType}\`, {...})` for this case — but `sapPost` always prefixes `sapConfig.url` (SapServer's own base URL, confirmed from `config.js`'s import), and SapServer has no `/drumming/*` routes at all (confirmed directly against `SapServer/Controllers/ProductionController.cs` — its real combined endpoint is `POST api/production/drumming-backflush`). The body Node sends there (`TotalLength`/`Order`) doesn't even match that endpoint's real request DTO's field names either, meaning every non-concession DR retry would 404 in production. This isn't the kind of confirmed-in-production quirk this migration otherwise preserves (like `drumRef`'s hyphenation, or `SapPad`'s real behavior documented in SapServer's own `CLAUDE.md`) — it's an unexercised, broken path that would only ever be hit on the rarer non-concession DR retry. Ported to call the correct `api/production/drumming-backflush` endpoint instead, resolving fresh traceability materials via `DrummingHelper.ResolveTraceabilityMaterialsAsync` (made `internal` for this reuse) the same way the original submission does — matching what a *working* retry needs to do, not what Node's broken one actually sends.
- **DR's hard block re-checks against the *persisted* BOM snapshot (`BomHelper.LatestBomSnapshotAsync`), not a fresh SAP re-download** — a real, correct difference from `DrummingHelper.SubmitAsync`'s own hard block (which uses the just-downloaded in-memory rows from the same request): this is a retry of the *same* job, potentially long after the original submission, so it must validate against what was actually saved (and possibly since "Refresh BOM"-ed), matching Node's own `latestBomSnapshot(pool, 'DR', id)` call in the retry route exactly.
- **DR retry's `SAPPostings` insert omits `SAPBatchNumber` entirely, unlike `DrummingHelper.SubmitAsync`'s own non-concession branch** — a real, narrower omission in Node's retry route itself (its INSERT statement genuinely has one fewer column here), preserved as-is rather than "fixed" to match the original submission's shape.
- **The `BLOCKED` outcome (DR only) is a genuine HTTP 409 with `success:false` — same real convention `DrummingSubmitResult` already established** for the original submission. One small, deliberate shape difference: Node's retry route echoes `drummingID` inside its `data` payload (`res.status(409).json({ success:false, data:{drummingID:id,status:'BLOCKED'}, error:errMsg } )`); this port's shared `FailedBackflushRetryResult` (used by every branch, not DR-specific) has no such field, so the C# response's `data` carries just `{status:'BLOCKED', ...}` without the id. Harmless in practice — the id is already in the URL the caller just PATCHed — but a real, intentional simplification worth naming rather than silently dropping.
- **EX's `Cannot retry` billet-staging failure is a plain `NexusConflictException` (409, no `data` payload)** — genuinely different in shape from DR's `BLOCKED` result (which is a *returned value*, not a thrown exception, so it can carry a `data` payload) — matches Node's own `res.status(409).json({ success:false, error:'Cannot retry — ...' })` (no `data` key at all) exactly.
- **The shared catch (every branch except MX, which handles its own per-tub failures internally) maps a genuine SAP/DB failure to a real HTTP 502** via `NexusBadGatewayException` — no `SAP_FAILED`-200 grace period here, unlike `DrummingHelper.SubmitAsync`/`MetreProcessHelper.CompleteAsync`'s own convention for a *first* submission failing. Matches Node's own `res.status(502).json({ success:false, error:errMsg })` for a retry that fails again — a supervisor retrying from this queue gets a real error, not another silent queue entry.
- **`GET failed-backflush`'s 9-way `UNION ALL` is built dynamically off `ProductionSapHelpers.Process`/a literal process-code list**, same style already established for `MetreProcessHelper.GetOpenRunsAsync`'s near-identical multi-process union query, rather than hand-written per branch — deliberately excludes FW (no `Status=6` union branch for it in Node either, matching the "not yet implemented" retry fallthrough above).
- **`PATCH .../cancel` has no rows-affected check** — an unconditional `UPDATE ... WHERE Status = 6` followed by an always-written event log entry and always-200 response, even if the record has since moved on (retried successfully, already cancelled) — matches Node's own route exactly, which never checks `rowsAffected` either.
- All three new routes are `[Authorize(Policy = "Perm:" + ProductionReportsHelper.FnSupervisor)]`-gated, reusing the existing `PROD_SUPERVISOR` policy constant already wired up for `open-runs`/`history`/`trace`/`scrap`/`reversal` — matching Node's own `requirePermission('PROD_SUPERVISOR')` on all three routes exactly.
- 2 new `FailedBackflushHelperTests` — `RetryAsync` opens a connection unconditionally before dispatching (the process code itself picks the branch, there's no request-shape check that could reject early the way every other Helper's validation does), so only `CancelAsync`'s unknown-process-code guard is unit-testable without a live SQL Server/SapServer; a second test confirms MX (special-cased with a hardcoded table/pk in Node's own cancel route, unlike this port's uniform `ProductionSapHelpers.Process` lookup) isn't mistakenly rejected as unknown. Real HTTP smoke test confirms all 3 new routes return 401 unauthenticated.

### Sub-phase 6c, fifth slice: Drumming Ticket, Order Lookup, coils/reversal-status/data

`GET drumming/data`, `GET drumming/:id/coils`, `GET drumming/:id/reversal-status`, `GET order-lookup`, `GET order-lookup/by-order/:orderNumber`, `GET drumming/ticket/:referenceDocument/:item/print` — the last of Sub-phase 6c's own "still real, tracked, unbuilt scope" list from the third slice. Closes out Drumming and Sub-phase 6c entirely; Sales/Production's shared `production-schedule` cluster and Sub-phase 6b's Batch History/Traceability reports were the only other consumers of `log.AgreementSnapshot`-style data before this.

- **`GET drumming/ticket/:referenceDocument/:item/print` is a genuinely different response shape from every other route in this controller — it returns raw `text/html`, not the JSON `ApiResponse<T>` envelope**, meant to be opened directly in a new browser tab (`window.open(..., '_blank')`) which auto-triggers `window.print()` on load — the OS-native print dialog, not the network-printer TCP flow `LabelPrintHelper` uses for production labels. `LabelsController.PreviewProcess` (Sub-phase 6b) already established this exact pattern — a data-fetch Helper (`OrderLookupHelper.LoadTicketDataAsync`) throwing the normal `NexusApiException` family on failure (still converted to JSON by `ApiExceptionMiddleware`, since this route sits under `/api/productionnexus` like everything else — a real, accepted asymmetry: only the *success* path is raw HTML) plus a separate, pure string-building Helper (`DrummingTicketHtmlHelper`, mirroring `LabelHtmlHelper`'s own split) for the render itself — followed here rather than inventing a new convention.
- **`GET api/production/order-text/{salesDocument}/{item}` is a plain path-segment SAP GET (no request body), confirmed directly against `SapServer/Controllers/ProductionController.GetOrderText`** — the first SapServer call in this migration that isn't the established "GET-with-a-JSON-body" shape (`BomQuery`/`ProfitCentreRequest`/etc.) — `ISapServerClient.GetAsync<T>`'s `body` parameter already defaults to `null` for exactly this case, so no client-side change was needed, just a call site that omits it. Deliberately **not cached** — a live lookup on every print, per the "process critical" instruction the original Node code's own comment records — a SAP failure here degrades to an inline `[Could not reach SAP for special instructions: ...]` message on the printed ticket rather than failing the whole page, matching Node's own try/catch around `sapGet` exactly.
- **`ReferenceDocument`/`Item` throughout this slice are `OriginalDoc`/`OriginalDocItem`, not `log.AgreementSnapshot`'s raw `ReferenceDocument`/`Item` columns** — without this aliasing, an operator searching by order number (or reprinting a ticket) for a line that's just been picked would get "no open items found," because SAP has already flipped that line's raw `ReferenceDocument` to a delivery number by then. `AgreementLookupRow`/`AgreementLookupColumns` (shared by `SearchAsync`, `GetByOrderAsync`, and `LoadTicketDataAsync` — one column list, three call sites, matching Node's own single `AGREEMENT_LOOKUP_COLUMNS` constant) alias this at the SQL layer so every consumer sees a plain `ReferenceDocument`/`Item` field regardless.
- **The printed ticket's `RequiredQty` formatting (`#,##0.###` under `en-GB`) approximates JS's `toLocaleString('en-GB', { maximumFractionDigits: 3 })`** — trims trailing zeros (matching a whole-number quantity rendering as `400`, not `400.000`) while keeping thousands separators, the first place in this migration a JS-style trimmed-decimal display had to be reproduced server-side in C# rather than left to a client-side JS formatter (`reports-common.js`'s `fmtNum` and friends do the equivalent client-side elsewhere) — because this whole page is rendered on the server, not hydrated from JSON.
- **The 35-slot, 3-column hand-fill coil checklist (`DrummingTicketHtmlHelper.CoilCol`) is unrelated to `prod.DrummingCoils`** — a fixed paper-grid layout matching the Excel Ticket tab's operator grid (columns 1–12/13–24/25–35, `Math.Ceiling(35/3)`), not a rendering of the coil-length rows an operator actually enters at submission time (`GET drumming/:id/coils`, a completely separate, genuinely tiny endpoint reading `prod.DrummingCoils` directly). Two unrelated "coil" concepts sharing a name, preserved as two separate, unconnected pieces exactly as Node has them.
- **`GET drumming/:id/reversal-status` is deliberately a *client-side convenience only*** — Node's own comment calls it out explicitly as "quick check for the traceability safeguard's instant client-side feedback," with `DrummingHelper.AssertParentBatchesReversedAsync` (third slice) remaining the sole authoritative, server-enforced check applied at actual submission time. This port's `GetReversalStatusAsync` throws `NexusNotFoundException` for an unknown `drummingId` (404), matching Node's own explicit `if (!r.recordset.length) return res.status(404)...` check — the one place in this slice with a real not-found guard; every other new read here (coils, drumming/data, order-lookup's plain search) just returns an empty result set for an unmatched filter, same as Node.
- **`drumming/data`'s query DTO follows the exact `MetreProcessHelper.GetDataAsync`/`MetreProcessDataQuery` precedent** (`DateTime.TryParse` for optional from/to bounds, `LIKE '%...%'` wildcarding for text filters) — a straight, unremarkable reuse of an already-established pattern, nothing new to say about it.
- 6 new tests: 4 `DrummingTicketHtmlHelperTests` (pure string-building, no I/O — same fully-real-testable category `LabelHtmlHelperTests` already established, covering the order reference/customer details, the SAP/customer-instructions empty-state placeholders, all 35 numbered coil-checklist cells across 3 tables, and HTML-encoding) + 1 `OrderLookupHelperTests` (the one pre-connection validation path — `SearchAsync` rejecting a search with neither `material` nor `customer`). Real HTTP smoke test confirms all 6 new routes return 401 unauthenticated.

The soft cross-department dependency flagged in the third slice (`AssertParentBatchesReversedAsync` needs Warehouse's not-yet-ported `redrumReversal.js` to ever actually set `prod.Drumming.IsReversed`) remains open, expected, and tracked for Phase 7 — not a gap introduced by this sub-phase's own sequencing. Frontend for the entire BOM-validated wizard, Drumming's entry form, and this slice's Order Lookup/Drumming Ticket pages is still deliberately deferred, same reasoning recorded at each backend slice above: real, substantial standalone UI work that doesn't fit any existing page shape, scoped separately rather than rushed.

### Sub-phase 7a, second slice: Open Picksheets, Packaging Holding, and the SAP-backed picking-materials panel

`GET api/deliverymain/id/:id`, `/open-picksheets`, `/packaging-holding`, `/:id/picksheet-materials`, `/:id/linked-picksheets`, `/link-search` (`WarehousePicksheetHelper`) — the read-only cluster split off from the master-data slice once research showed `getRemainingRequiredMaterials`'s SAP orchestration, European-decimal parsing, and staging-bin conflict logic is a different scale of work from plain CRUD. `landing-sparkline` (also in `deliverymain.js`) is deliberately excluded — confirmed via `private/js/landing.js` that it's one of three per-department sparkline widgets on the portal's own dashboard page, a cross-cutting concern nothing in this migration has built yet (Production's own `landing-sparkline` wasn't ported during Phase 6 either), not something for one department's own phase to pick up piecemeal.

- **A significant, genuine discrepancy from Node was found here and deliberately NOT silently perpetuated into more code: Node's own SAP calls all authenticate as a fixed placeholder, not the real calling user.** `deliverymain.js`'s local `makeSapToken()` (and the identical one in `productionnexus.js`, and `sap.js`'s own exported version — confirmed by reading all three) always signs `{ userId: 0 }`, with `productionnexus.js`'s own copy carrying an explicit `// TODO: include user info in token if needed for SAP logging; currently just a placeholder`. This port's `ISapServerClient`/`SapServerClient.MakeSapToken(userId)` has embedded the *real* calling user's ID in every SAP call since Sub-phase 6b's own `MakeSapToken` doc comment claimed it "matches sap.js's makeSapToken exactly" — which, per this direct read of Node's actual source, it does not. **Not changed here** — reverting to Node's placeholder-0 behavior would be a cross-cutting change touching every previously-shipped department (Engineering through Production), not something to slip in as a side effect of one Warehouse slice, and it's plausible the real-userId design was a deliberate, considered improvement over Node's own TODO-flagged wart rather than an oversight (SapServer's permission model is genuinely built around real per-user `PortalUserDepartments` resolution, which a fixed userId:0 could never exercise correctly). Flagged here prominently, unresolved, for a deliberate decision once real login/permission data against a live SapServer exists to actually observe which behavior the two systems' current production deployment relies on.
- **`ParseSapQuantity` deliberately does NOT port Node's own `parseSapNum` bug-compatible.** Node's `parseSapNum` (duplicated identically in `getRemainingRequiredMaterials` and `getDeliveryQuantityMatch`) assumes every SAP quantity string is European-grouped, unconditionally stripping any period whenever no comma is present — the exact fixed-format assumption **SapServer's own `CLAUDE.md` already documents as confirmed wrong** for this SAP system's genuinely mixed-format data (the real, production-confirmed 1000x-inflation bug that motivated `RfcRowExtensions.ParseSapDecimal`'s per-value last-separator-wins fix). SapServer's `PicksheetHelpers.ParseStockRows`/`ParseLipsRows` return these exact same raw, unparsed strings with no server-side correction (confirmed by reading that source directly), so the client is responsible for parsing them either way — this port applies the already-proven-correct algorithm instead of Node's, ported directly from `RfcRowExtensions.ParseSapDecimal`'s own logic. Verified with a real unit test (`ParseSapQuantity_resolves_the_real_decimal_point_per_value`) covering the exact case Node's version would get wrong: a plain invariant decimal like `"1234.56"` with no comma at all.
- **`GET id/:id` keeps Node's real `SELECT *` scope as a full known-column `DeliveryMainRow` DTO, not trimmed to the one field (`picksheetComment`) every confirmed frontend caller actually reads** — a generic "get delivery by ID" read is exactly the kind of endpoint a not-yet-built page is likely to need more of later; trimming it now would just mean re-widening it in a future slice for no real benefit today.
- **`WAREHOUSE_OP` is Warehouse's own widest-reaching legacy code, kept unsplit for this slice** — same deferred-per-tile-split precedent Production's Sub-phase 6a set for `PROD_SUPERVISOR`; `WarehousePicksheetHelper.FnOp` holds the literal string for now, reused via `[Authorize(Policy = "Perm:" + WarehousePicksheetHelper.FnOp)]` on `open-picksheets`/`packaging-holding`/`picksheet-materials`/`link-search` — matching Node's own per-route `requirePermission('WAREHOUSE_OP')` calls exactly. `linked-picksheets` and the generic `id/:id` read have no permission gate in Node either, and none was added here.
- **`link-search`'s required `excludeDeliveryId` is bound as a nullable `long?`, not a bare `long`** — a required non-nullable `[FromQuery]` value type on an `[ApiController]` would trigger ASP.NET Core's own automatic 400 (a generic `ValidationProblemDetails`, not this app's `ApiResponse<T>` envelope) before the action even runs. Validated inside `LinkSearchAsync` instead (`NexusValidationException` when null), matching this migration's own established "validate in the Helper, not via framework auto-validation" convention everywhere else, and preserving Node's own custom error message shape.
- 9 new `WarehousePicksheetHelperTests` — 8 cover `ParseSapQuantity` directly (pure logic, no I/O, fully real-testable — European-grouped, comma-only, plain-invariant, integer-only, US-grouped, and empty/null/unparseable inputs) + 1 covers `LinkSearchAsync`'s pre-connection validation path. Real HTTP smoke test confirms all 6 new routes return 401 unauthenticated.

### Sub-phase 7b: the pallet/package builder + staging reversal

`GET/POST/PATCH api/palletmain`, `GET/POST/PATCH/DELETE api/palletpackages` (`PalletMainHelper`/`PalletPackagesHelper`), plus `routes/sapStaging.js`'s shared `reverseStagedPackage` (`SapStagingHelper`) — port of `palletmain.js`/`palletpackages.js`, the core of the pallet builder. Neither Node file imports `requirePermission` at all — both mounts are `requireLogin`-only in `server.js`, kept exactly (no policy added on any action).

- **Only the routes with a confirmed live frontend caller are ported, same discipline as every earlier Warehouse slice** — `GET id/:id`, `POST /`, `PATCH /:id` on both files, plus `palletpackages.js`'s `GET pallet/:palletId` and `DELETE /:id`. `palletmain.js`'s bare `GET /`, `GET /category/:c`, and `GET /location/:l`, and `palletpackages.js`'s bare `GET /`, `GET /id/:id`, `GET /sapdelivery/:id`, and `GET /sapmaterial/:id` all have zero confirmed callers and are not ported. `landing-sparkline` (also in `palletmain.js`) is excluded for the same cross-cutting-dashboard-widget reason as `deliverymain.js`'s own copy in the previous slice.
- **`reverseStagedPackage` is genuinely shared, load-bearing infrastructure, ported once as `SapStagingHelper.ReverseStagedPackageAsync`** — both a pallet removal (`PalletMainHelper.UpdateAsync`, reversing every package on the pallet) and a single package delete (`PalletPackagesHelper.DeleteAsync`) depend on it. `SapServerClient.PostAsync` already throws a `NexusApiException` for SapServer's real 422-rejection case, which this method catches and converts into the graceful `Attempted:true/Success:false` result the caller needs — mirroring Node's own try/catch shape without needing to duplicate SapServer's success/failure envelope inspection by hand.
- **Both "fails closed" reversal paths are preserved exactly**: a pallet is not marked removed, and a package is not deleted, unless every SAP reversal it depends on actually succeeded — matching Node's own explicit reasoning comments (there's no atomic multi-call SAP transaction available, so a partial failure must leave the app and physical/SAP reality unable to disagree about where stock is, rather than silently proceeding). Pallet removal's 422 response carries a structured `Failures` list (one entry per package that couldn't be reversed); package delete's 422 is a plain message, matching the real difference in Node's own two response shapes (`{success:false,error,failures:[...]}` vs `{success:false,error}` — a single string with `${reversal.error} — package was not removed}` appended).
- **`PalletUpdateResult` is a Helper-returned value, not a thrown exception, for the reversal-blocked case** — same "Helper returns a result, controller maps it to the right HTTP status with a manually-constructed `ApiResponse`" pattern Sub-phase 6c's `DrummingSubmitResult`/`FailedBackflushRetryResult` already established for a `success:false` response that also needs to carry a structured `data` payload alongside its error, which `ApiResponse<T>.Fail` alone can't do.
- **`UpdatePalletRequest`'s partial-update semantics collapse "field omitted" and "field explicitly `null`" into the same behavior (leave the column alone), via `COALESCE(@x, column)` for every field** — a deliberate, small simplification over Node's own `!== undefined` presence check, which would let an explicitly-sent JSON `null` attempt to null out a `NOT NULL` column; no confirmed caller ever does this, and the simplified version is strictly safer. The "nothing to update at all" 400 is preserved via an explicit `HasAnyUpdateValue` check across every field before the `UPDATE` runs, rather than trying to infer it from the `SET` clause the way Node's dynamically-built `sets[]` array does.
- **`palletFinish`'s side effect (also stamping `palletFinishDate = GETDATE()`) only fires on an explicit `true`, matching Node's own truthy check** — sending `palletFinish: false` (a real, valid value, not an absence sentinel) correctly leaves `palletFinishDate` untouched, same as omitting the field entirely; only `palletFinish: true` stamps it.
- 4 new `PalletPackagesHelperTests` (every pre-connection validation path on `PalletPackagesHelper.UpdateAsync` — neither field provided, non-positive `palletLayer`, blank `packagingID`). `PalletMainHelper.UpdateAsync` has no pure pre-connection validation path to test (every call opens a connection first, same as Node's own `getPool()`-before-anything-else shape) — no forced test written for it. Real HTTP smoke test confirms all 7 new routes return 401 unauthenticated.

### Sub-phase 7c, first slice: the delivery completion pipeline

`PATCH api/deliverymain/:id/complete` + `POST api/deliverymain/:id/sync-delivery-quantities` (`DeliveryCompletionHelper`) — port of `completeOneDelivery`/`runZdelflagMaintenance`/`runGoodsIssueApproval`/`getDeliveryQuantityMatch` and their two route handlers. The single highest-risk cluster in Warehouse — real SAP goods movements (ZDEL weight push, ZDELFLAG/ZDELPACK maintenance, Goods Issue, delivery-quantity correction), not just reads or reversible reversals.

- **A confirmed, live bug in Node's own Goods Issue call was found and fixed — in Node itself, not just this port — per explicit user direction ("update node to match sap server, as this was confirmed working using manual curls").** `runGoodsIssueApproval` was posting `POST /api/warehouse/goods-issue` with only `{DeliveryNumber}`. SapServer's own integration moved from `BAPI_DELIVERYPROCESSING_EXEC` (never worked live) to `BAPI_OUTB_DELIVERY_CONFIRM_DEC` (`GoodsIssueModels.cs`'s header comment), confirmed live 2026-08-28 that `POST_GI_FLG` alone isn't enough — SAP rejects with "Delivery has not yet been put away / picked (completely)" unless `Items` also carries each real delivery item's picked quantity (`ITEM_DATA_SPL-QTY_POST`). Node's `routes/deliverymain.js` was updated directly (not just this C# port) to build `Items` from `log.PalletPackages` (`SUM(sapQuantity)` grouped by `sapDeliveryItem`, real batches only — `sapMaterial IS NOT NULL`), the same source/grouping `getDeliveryQuantityMatch` already uses; its 3 `goods-issue/reprocess` tests reaching this code path were updated to match and now assert the real `Items` payload is sent, not just deleted/skipped. **This landed on `dotnet-rewrite`, not `main`** — flagged to the user as a genuine production bug fix that won't reach the live Node app until this branch merges (not before cutover per the PR description), pending their decision on whether to cherry-pick it to `main` directly.
- **A second, separate, NOT-yet-confirmed contract gap was found while porting `sync-delivery-quantities` and deliberately left unfixed, unlike Goods Issue** — `POST /api/warehouse/delivery-change` (`BAPI_OUTB_DELIVERY_CHANGE`) needs `BaseUom`/`SalesUnit`/`FactUnitNom`/`FactUnitDenom` per `DeliveryChangeModels.cs`'s own extensively-documented live diagnosis timeline (confirmed 2026-08-28 that `BASE_UOM` alone caused `VLBAPI 004`/`VL 268` until those other fields were also supplied); `SapDeliveryChangeItem` on this side (and Node's own `sync-delivery-quantities` route) has only ever sent `ItemNumber`/`Material`/`Quantity` — no `BaseUom` at all, which `BuildDeliveryChangeRequest` defaults to a bare empty string when absent. Unlike Goods Issue, this was **not** confirmed working via a live curl test, so — per the explicit distinction the user drew between the two — this port faithfully mirrors Node's current (quite possibly still-broken) behavior rather than guessing at a fix. Documented prominently on `SapDeliveryChangeRequest`'s own doc comment in `WarehouseSapModels.cs` and here, for the same kind of deliberate live-curl verification Goods Issue just got, whenever that's next convenient.
- **A third, systemic finding, orthogonal to both of the above: `SapServerClient.PostAsync`/`GetAsync` discard SapServer's structured error `data` payload on any failure response, keeping only the flat `error.Message` string.** Confirmed by reading `SapServerClient.SendAsync`'s exception path directly (`throw new SapProxyException(statusCode, error?.Code, error?.Message)` — `envelope.Data` is never read on the failure branch) against SapServer's own `WarehouseController.PostGoodsIssue`, which returns `ApiResponse<GoodsIssueResponse>.Fail("422", "...", response)` — a real 3-argument `Fail` overload that embeds the full `GoodsIssueResponse` (including its own granular per-item SAP `RETURN` messages) in `data` alongside the generic error string. Node's own `runGoodsIssueApproval`/`sync-delivery-quantities` explicitly prefer `err.response?.data?.data?.messages` over the generic error message specifically to surface that per-item detail — this port's equivalent `catch` blocks only ever see the flattened `err.Message`, a real (if graceful) loss of diagnostic granularity on every 422 across every department this migration has built so far, not something introduced by this slice. Not fixed here — a `SapServerClient` redesign (an `object? Data` on `SapProxyException`, or a `TryPostAsync` returning the failure envelope structurally) is a cross-cutting architectural decision affecting every previously-shipped phase, out of scope for one Warehouse slice — flagged for a deliberate decision, same treatment as the `userId:0` finding from the previous slice.
- **`GetDeliveryQuantityMatchAsync`'s per-item classification (`exact`/`within-tolerance`/`exceeds-tolerance`, `Epsilon`/`Tolerance` constants) is a direct, faithful port of Node's own math** — including the `pctDiff` special case for `requiredQty == 0` with something picked (treated as maximally over tolerance, `decimal.MaxValue`, rather than dividing by zero) — nothing simplified or changed here, unlike the two BAPI-contract items above.
- **`CompleteGroupAsync`/`SyncDeliveryQuantitiesAsync` both use the established "Helper returns a result, controller maps it to the right HTTP status" pattern** (`CompleteDeliveryGroupResult`/`SyncDeliveryQuantitiesResult`) — `CompleteGroupAsync`'s `BLOCKED` status carries the same structured `Outstanding` per-delivery breakdown Node's own 409 response does; `SyncDeliveryQuantitiesAsync` collapses Node's three distinct failure shapes (two different 409 messages, one 422-with-per-delivery-prefix) into one `(Success, StatusCode, Error)` triple, since — unlike `CompleteGroupAsync`'s `Outstanding` — none of Node's three failure cases actually needs a structured data payload beyond the message itself.
- **`RunZdelflagMaintenanceAsync`'s row-building (`BuildDelflagRows`) is a direct, unabridged port of Node's own pallet/package iteration** — the owner-vs-borrowed-pallet header-row skip, the `PACKID = palletID*1000 + n` numbering, the `delpackWarnings` data-quality checks (a missing packaging instruction, or one with no `ZBOM_INFO` components, silently sends an empty `T_DELPACK` that SAP itself won't complain about) all preserved exactly, per `ZdelflagHelpers.cs`'s own header comment on the SapServer side confirming this exact row shape.
- **No new Helper tests this slice** — every method here (`GetDeliveryQuantityMatchAsync`, `RunZdelflagMaintenanceAsync`, `RunGoodsIssueApprovalAsync`, `CompleteOneDeliveryAsync`) takes a `SqlConnection` directly rather than `INexusOperationsDb`, and `CompleteGroupAsync`/`SyncDeliveryQuantitiesAsync` both open a connection unconditionally as their first statement with no validation ahead of it — matching Node's own `getPool()`-before-anything-else shape exactly, so there's no pure pre-connection path to test, same caveat class as `PalletMainHelper.UpdateAsync` in the previous slice. Real HTTP smoke test confirms both new routes return 401 unauthenticated; the full existing suite (196 tests) still passes unchanged.

### Sub-phase 7c, second slice: the ZDELFLAG/Goods Issue warning-log queues

8 routes (`GET zdelflag/warnings`, `GET :id/zdelflag/status`, `POST :id/zdelflag/reprocess`, `POST :id/zdelflag/resolve`, and the same 4 for `goods-issue`) — port of `routes/deliverymain.js`'s last 8 handlers (lines ~1721–1970), all still on `DeliveryCompletionHelper`/`DeliveryMainController` since they're just a thin read/gate layer directly on top of the same `log.DeliveryZdelflagRun`/`log.DeliveryGoodsIssueRun` tables and the same `RunZdelflagMaintenanceAsync`/`RunGoodsIssueApprovalAsync` methods the first slice already built.

- **Self-caught bug, fixed before this slice's own new code could compound it**: the first slice's `RecordRunAsync` closures (inside `RunZdelflagMaintenanceAsync`/`RunGoodsIssueApprovalAsync`) were serializing `messages` with bare `JsonSerializer.Serialize(messages)` — default PascalCase — into the exact same `messages` NVARCHAR(MAX) column Node's own `JSON.stringify(messages)` writes lowercase `type`/`message` keys into, and that this slice's own new `GetWarningsAsync`/`GetStatusAsync` now read back. Left as-is, every row this app itself wrote would have silently failed to deserialize correctly for Node's still-running `JSON.parse`, and — the more immediate risk — for this slice's own `DeserializeMessages`, since a PascalCase `Type`/`Message` payload doesn't bind onto `SapReturnMessage`'s JSON contract without the same options being used both ways. Fixed by adding a shared `MessagesJsonOptions = new(JsonSerializerDefaults.Web)` field and applying it at both write call sites; this slice's own new `DeserializeMessages` helper uses the same field, so read and write are now guaranteed to agree.
- **The warnings queues (`GetWarningsAsync`) are a latest-row-per-delivery join, not a plain `WHERE status IN (...)` scan** — mirrors Node's own subquery (`INNER JOIN (SELECT deliveryID, MAX(ranAtUtc) ... GROUP BY deliveryID) latest`) exactly: a delivery that failed once but has since succeeded (a newer row with `status='Success'`) must not still show up in the warnings list just because an old `Failed` row exists in its history. ZDELFLAG's queue includes both `Failed` and `Warning` statuses; Goods Issue's includes only `Failed` — there's no `Warning` outcome for Goods Issue in either app, confirmed by re-reading Node's own route (`WHERE r.status = 'Failed'`, no second value).
- **The 4 reprocess/resolve gates are read-then-throw, using the same `NexusConflictException` → 409 pattern already established across every other Warehouse Helper this phase** (`PalletMainHelper`'s reversal-blocked path, etc.) rather than a new result-wrapper type — unlike `CompleteGroupAsync`'s `BLOCKED` status, none of these four needs to carry a structured payload beyond the message, so throwing (letting `ApiExceptionMiddleware` do the mapping) is the simpler and more consistent choice here. Gate conditions ported exactly from Node: ZDELFLAG reprocess 409s only when the latest run is already `'Success'`; Goods Issue reprocess 409s when ZDELFLAG's latest run is anything other than `'Success'` *or* when Goods Issue's own latest run is already `'Success'` (both checked, first failure wins — matches Node's two sequential `if` blocks); both resolve endpoints 409 unless the latest run is in the resolvable state for that queue (`'Failed'`/`'Warning'` for ZDELFLAG, `'Failed'` only for Goods Issue — consistent with the narrower Goods Issue status set above).
- **Resolve inserts a synthetic `'Resolved'` row rather than updating the failed one in place** — matching Node's own `INSERT`-not-`UPDATE` (the run history table is append-only; "resolved" is itself just a new latest-status row, so the same latest-row-per-delivery join used everywhere else picks it up automatically without a schema or query change). Note text falls back to `"Manually marked resolved by {username}."` when the caller sends a blank/omitted note, exactly matching Node's `note || `Manually marked resolved by ${username}.`` — both `ResolveZdelflagAsync`/`ResolveGoodsIssueAsync` take the new `ResolveRunRequest(string? Note)` DTO.
- Both resolve actions are gated `[Authorize(Policy = "Perm:LOG_SUPER")]` (a literal string, matching `WarehouseMasterDataController`'s existing precedent for a permission code with no per-tile Helper constant of its own) rather than `WarehousePicksheetHelper.FnOp` — mirrors Node's `requirePermission('LOG_SUPER')` on exactly these two routes (a stricter gate than the plain `WAREHOUSE_OP` every other route in this controller uses), confirmed by re-reading the Node source directly rather than assuming the same permission as its sibling reprocess/status routes.
- **No new Helper tests this slice either** — same reasoning as the first slice (every method takes a `SqlConnection`/opens one unconditionally as its first statement, no pure pre-connection validation path exists to test in isolation). Real HTTP smoke test (`dotnet run` + `curl`) confirms all 8 new routes return 401 unauthenticated with no 404/500; `dotnet build`/`dotnet test` both clean (196 existing tests still pass, unchanged from the first slice since none of this slice's new code is reachable from a pure/testable entry point).

## Hosting

**IIS via ASP.NET Core Module v2, in-process hosting model** (the ASP.NET Core Web App template's default `hostingModel="inprocess"` in the generated `web.config` — the app runs directly inside the IIS worker process, not as a separate Kestrel process behind a reverse proxy). No `UseWindowsService()` — a deliberate departure from how the Node app is hosted today (a genuine Windows Service via `node-windows`/WinSW), per explicit user preference, and also means this app ends up hosted the same way as the sibling `SapServer` repo (both IIS sites), even though the two stay separate deployed apps.

IIS hosting carries real gotchas already confirmed painfully for real on SapServer this same session (see `/home/user/SapServer/CLAUDE.md`'s "Critical Platform Constraints") that this app's own `install.ps1`/app-pool config will need to account for once they're written:
- App pool default `OnDemand` start mode delays all startup code (DI, any background scheduler) until the first real request — needs `startMode=AlwaysRunning` + `preloadEnabled=true` + IIS Application Initialization (the `/health` endpoint above is what it would warm).
- `ApplicationPoolIdentity` needs explicit `icacls` grants (read+execute on site root, Modify on any writable path) and `processModel.loadUserProfile=$false`.
- App-pool recycling can kill an in-flight Quartz.NET job — a risk the old Windows-Service hosting didn't have. Needs either `idleTimeout=00:00:00` + recycling disabled, or every scheduled job made safely resumable across a restart. Not yet decided — no Quartz.NET jobs exist yet (Phase 10).
